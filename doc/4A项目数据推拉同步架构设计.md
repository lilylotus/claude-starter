# 4A项目数据推拉同步架构设计

## 一、总体思路

4A项目里"机构/人员/任职"数据向下游应用同步，本质上是一个**主数据分发**问题。核心思路是：不要把"推"和"拉"设计成两套独立系统，而是让它们共用同一个"变更日志"数据源，推送做实时性，拉取做可靠性兜底，两者互为补偿。

整体架构闭环：

```
业务系统数据变更（机构/人员/任职）
        ↓
变更流水表（全局seq，entity_id + version + seq）
        ↓                              ↓
   推送通道                          拉取通道
（MQ/Webhook 轻量通知）        （增量/全量 API + 游标）
        ↓                              ↓
              应用侧处理（幂等更新 + 记录游标）
                        ↓
              定期对账校验（摘要/hash比对）
                        ↓
              触发补偿拉取 → 回到"拉取通道"
```

---

## 二、数据模型：一切设计的基础

每类主数据（机构/人员/任职）除了业务字段外，补三个字段：

- **全局唯一ID**（entity_id）
- **version**（乐观锁版本号，每次修改+1）
- **update_seq**（不是时间戳，是全局单调递增的序列号，避免同一毫秒多条变更冲突、避免时钟回拨问题）

再单独建一张**变更流水表**（change_log），是整个方案的核心：

```
change_seq     -- 全局自增主键，也是游标
entity_type    -- ORG / PERSON / POSITION
entity_id
operation      -- INSERT / UPDATE / DELETE
change_time
org_scope_path -- 冗余存该数据所属的机构路径，方便按范围过滤
```

推送和拉取都从这张表出，保证两条通道数据完全一致。

---

## 三、拉取（Pull）：按范围增量/全量

### 增量拉取接口

```
GET /api/changes?since_seq=10086&entity_type=PERSON&org_scope=ORG001&page_size=500
返回: { records: [...], next_seq: 10600, has_more: true }
```

- 用 `change_seq` 做游标而非时间戳——时间戳会重复、会因时钟回拨倒退，seq严格递增，应用只需存"上次拉到的seq"，下次从那继续，天然支持断点续传。
- 按 `entity_type` + `org_scope`（机构树范围）过滤，即"指定数据范围"的实现方式：给每个接入应用预先配置好可见的机构子树和数据类型。
- 分页用**游标分页**而非offset分页，避免数据不断写入时"漏页"或重复。

### 全量拉取接口

结构一样，用于应用首次接入或数据损坏后重建，直接查当前状态表（不查change_log），按机构范围分页拉取当前有效数据。

### 保证"不断拉取还不出错"的关键机制

- **幂等更新**：应用侧更新时判断 `本地version < 拉到的version` 才写入，防止重试重复数据或乱序覆盖。
- **游标持久化**：应用自己保存 `next_seq`，崩溃重启后从保存的seq继续。
- **游标过期兜底**：change_log不会无限保留（如90天），游标过期时接口返回明确错误码，提示应用转去做全量拉取。
- **对账接口**：提供数据摘要/hash校验接口，应用定期比对本地与服务端摘要，不一致则触发补偿拉取，是纠正"漏消息/漏拉取"的最后一道保险。

---

## 四、推送（Push）：变更通知

推荐**"轻量通知 + 应用回调拉详情"**：

- 变更写入change_log的同时，把 `{entity_type, entity_id, operation, change_seq}` 发到MQ（Kafka/RocketMQ）或调用应用的Webhook。
- 应用收到通知后，调用同一套拉取接口按entity_id或since_seq获取详情。

好处：推送和拉取复用同一数据出口，格式一致；推送消息体小，不用担心大对象超限。

### 保证推送可靠不丢的关键机制

- 用 **entity_id 作为MQ的分区/路由键**，保证同一实体的多次变更严格按顺序消费。
- 消费者用 `change_seq` 做幂等去重（Redis记录已处理seq或数据库唯一约束）。
- 推送失败需退避重试 + 死信队列，重试耗尽的进失败表，定时任务重推或人工介入。
- **最关键**：推送只是"加速通知"，应用侧无论是否收到推送，都应定期主动拉取一次"since last_seq"做补偿，不依赖推送100%可靠。

---

## 五、封装成SDK，让应用"接得住"

统一客户端SDK负责：

- 游标的保存与恢复
- 批量拉取与限流
- 失败重试
- 去重判断

拉取接口本身做限流保护（令牌桶），避免多应用同时全量拉取压垮服务端。明确错误码体系：`CURSOR_EXPIRED`（需转全量）、`NO_PERMISSION`、`RATE_LIMITED`、`PARAM_INVALID`。

## 六、change_log 大数据量的调整方案

**关键原则：change_log 不应该按应用复制多份**，一份变更只应该存一条物理记录，否则数据量 = 变更数 × 应用数，很快爆炸。

### 1. change_log 保持全局唯一一份
只增长"变更数"这一个维度，跟应用数量无关。

### 2. 应用消费进度单独存
```
app_cursor
app_id
entity_type
last_seq
update_time
```
这张表量级=应用数，几乎不增长。

### 3. "按应用范围过滤"在查询时算，不提前物化成N份
```sql
SELECT * FROM change_log 
WHERE change_seq > :last_seq 
  AND entity_type = :type
  AND org_scope_path LIKE :app_scope_prefix || '%'
ORDER BY change_seq LIMIT :page_size
```
用路径前缀匹配 + `(change_seq, org_scope_path)` 联合索引。只有应用数极多且权限逻辑复杂时，才引入轻量索引表（只存关联关系，不复制业务数据）加速。

### 4. 推送环节同理
一条变更只发一次消息到一个Topic，不同应用用各自的**消费组**读同一份消息（消息队列原生能力，不产生额外存储），过滤在Broker侧用tag/routing key或客户端SDK按org_scope过滤。

### 5. change_log 容量控制
- 只保留一个时间窗口（如90天），超期清理或转冷归档表。
- 游标落后太多超出窗口，返回 `CURSOR_EXPIRED`，提示转全量拉取。
- 全量拉取查当前状态表而非change_log，change_log数据量只取决于变更频率和保留窗口。
- 按时间分区（如按月），旧分区整体归档或drop。

**一句话总结**：变更数据只存一份，应用的消费进度只存一个游标，过滤和路由都是"查询时计算"而非"写入时复制"。

## 七、权限数据范围控制

### 1. 权限模型设计
给每个应用建范围配置表，而不是给每条数据打标签：

```
app_data_scope
app_id
entity_type      -- ORG / PERSON / POSITION / ALL
scope_type       -- INCLUDE / EXCLUDE
org_path_prefix  -- 机构树路径前缀，如 /1/12/
field_mask       -- 可见字段白名单或敏感字段黑名单
```

用机构路径前缀（如 `org_path = /1/12/121/`）而非枚举机构ID列表，机构树扩展时权限自动生效。支持INCLUDE + EXCLUDE组合处理"看全公司但排除某敏感部门"场景。

**任职数据要按"任职所在机构"判断**，而非人员主机构，避免漏掉跨机构兼职的任职记录。

### 2. 字段级权限（脱敏）
`field_mask` 配置字段白名单，在接口统一出参层做裁剪，保证推送和拉取口径一致。

### 3. 拉取时的权限执行
服务端解出app_id，查出该应用的app_data_scope，作为查询条件叠加（INCLUDE取交集、EXCLUDE取差集）。**必须在服务端强制执行**，不依赖应用自己传参过滤。返回前按field_mask裁剪字段。

### 4. 推送时的权限执行——建议两层过滤
- **第一层（消息路由，可粗）**：轻量通知（只含entity_id、变更类型）可走广播订阅，成本低。
- **第二层（拉取详情，必须精确）**：应用回调拉详情时严格执行第3点的权限过滤，没权限则返回空或403。

这种"轻量通知不设防、详情接口严格把关"的思路能平衡开发成本与安全性。

### 5. 权限变更时的处理
- **权限扩大**：服务端打标记/发特殊通知，提示应用针对新增范围做一次全量补拉。
- **权限缩小**：下发"移除通知"要求应用清理，或依赖定期对账机制自然发现并清理本地缓存。

### 6. 认证与审计
- 每个应用独立 `app_id + secret`，用HMAC签名或JWT做身份认证。
- 所有拉取/推送访问记审计日志：应用、时间、请求范围、返回条数，便于排查问题。
- 加调用频率限制，防止异常重试或权限边界扫描试探。

**一句话总结**：范围用机构路径前缀表达、字段用白名单表达，都配在"应用"维度而非"数据"维度；推送可分层做，但真正的权限判断只在服务端一处执行，推拉两通道复用同一套判断逻辑。
