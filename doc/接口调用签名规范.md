# 接口调用签名规范

本文档面向需要与本系统（RBAC 权限管理系统）进行数据同步对接的外部应用，说明对外接口的
鉴权方式、签名算法与验签规则，作为应用接入的统一规范。适用范围：

- **拉取（PULL）场景**：外部应用主动调用本系统的对外拉取接口获取变更数据。
- **通知（NOTIFY）场景**：本系统主动回调外部应用配置的通知地址，外部应用需按同一规则对
  收到的请求验签。

对应实现代码位于 `backend/src/main/java/cn/nihility/rbac/sync/sign/` 包下，本文档与实现
保持一致，如有出入以代码为准。

> **变更提示**：签名/验签相关的 5 个参数（`appKey`/`signMethod`/`ts`/`nonce`/`signature`）
> 现在统一通过**请求头**传递，不再放在 URL query 参数里（含原来的 `X-App-Key` 请求头，本次
> 也一并改名为 `appKey`）。这是不兼容变更，已按旧规范对接的应用需要同步调整调用方式。

## 1. 术语

| 术语 | 说明 |
| --- | --- |
| AppId | 对外应用标识（`open_app_id`），系统生成，全局唯一，24 位十六进制字符串 |
| AccessKey | 对外接口访问标识，系统生成，全局唯一，32 位十六进制字符串，请求时需携带 |
| SecretKey | 对外接口密钥，系统生成，48 位十六进制字符串，仅在重置接口的响应中明文出现一次，此后不可再查看，需妥善保管 |
| needSign | 应用配置的签名开关，为 `true` 时该应用的出站通知请求与入站拉取请求均需签名/验签 |
| signAlgorithm | 签名算法，取值 `SHA256`（HMAC-SHA256）或 `SM3`（HMAC-SM3，国密） |

AppId / AccessKey / SecretKey 由管理端「应用配置」功能生成和维护，外部应用不能自行生成，
需要通过管理员在后台获取（SecretKey 遗失需通过「重置 SecretKey」接口重新生成，旧值同时
失效）。

## 2. 签名参数

以下 5 个参数统一以**请求头**形式携带（无论是拉取请求还是通知回调请求），头名称均不带
`X-` 前缀，且与内部字段名/参数含义完全同名：

| 请求头 | 说明 |
| --- | --- |
| `appKey` | AccessKey，无论 `needSign` 是否开启都必须携带，用于定位调用方应用，同时参与签名 |
| `signMethod` | 签名方法，取值 `HMAC_SHA256` 或 `HMAC_SM3`，须与应用当前配置的 `signAlgorithm` 一致，`needSign=true` 时必填 |
| `ts` | 13 位毫秒级时间戳，`needSign=true` 时必填 |
| `nonce` | 随机数，用于防重放，建议使用不含分隔符的 UUID，`needSign=true` 时必填 |
| `signature` | 签名结果，见第 3 节，`needSign=true` 时必填 |

`appKey` 之外的 4 个头仅在应用开启 `needSign` 时才需要携带；`needSign=false` 时仍必须携带
`appKey`（用于定位调用方应用），但不需要也不校验其余 4 个头。

## 3. 签名算法

### 3.1 参与签名的字段

- 拉取请求（GET，无请求体）：URL 上的**全部**业务 query 参数（如 `dataType`、`bizIds`、
  `fromSequence`、`limit`）+ 请求头里的 4 个签名字段（`appKey`/`signMethod`/`ts`/`nonce`）。
  业务 query 参数与签名参数虽然分属 query 和 header 两个不同的携带位置，但都要参与同一次
  规范化拼接（详见 3.2）。
- 通知回调请求（POST，携带 JSON 请求体）：仅请求头里的 4 个签名字段
  （`appKey`/`signMethod`/`ts`/`nonce`，不含业务参数——通知回调请求本身不携带业务 query
  参数），另外单独对请求体原文签名，两段签名结果拼接。

### 3.2 规范化拼接（Canonicalize）

把参与签名的字段（不区分来自 query 还是 header，都作为普通的 key-value 对待）按 key 的
**ASCII 码升序**排列，以 `k1=v1&k2=v2&...` 的形式拼接：

- 值使用原始字符串值，**不做** URL 编码等二次编码。
- `signature` 本身不参与拼接（它是拼接结果算出来的）。
- 排序、拼接逻辑生成方（发起通知的一方）与校验方（接收拉取请求的一方）必须完全一致，
  否则签名比对会失败。

伪代码：

```text
canonicalize(fields):
    return join("&", ["{k}={v}" for k, v in sortByKeyAsc(fields)])
```

### 3.3 HMAC 计算

对规范化拼接后的字符串使用 SecretKey 明文作为密钥，按 `signMethod` 对应的算法计算 HMAC
摘要，取小写十六进制字符串：

- `HMAC_SHA256` → `HmacSHA256`，摘要长度 64 位十六进制字符。
- `HMAC_SM3` → HMAC-SM3（国密算法），摘要长度同为 64 位十六进制字符。

### 3.4 签名结果拼接规则

- **拉取请求（无请求体，仅 URL 签名）**：

  ```text
  urlSign = HMAC(secretKey, canonicalize({appKey, signMethod, ts, nonce, ...业务 query 参数}))
  signature = urlSign   # 64 位十六进制字符
  ```

- **通知回调请求（有请求体，URL 签名 + body 签名）**：

  ```text
  urlSign  = HMAC(secretKey, canonicalize({appKey, signMethod, ts, nonce}))
  bodySign = HMAC(secretKey, requestBodyRawJson)
  signature = urlSign + bodySign   # 128 位十六进制字符，直接字符串拼接，无分隔符
  ```

  `requestBodyRawJson` 为请求体的原始 JSON 字符串（未经任何转换的字节内容对应的字符串）。

`signature` 最终作为请求头 `signature` 携带，不放入 URL。

## 4. 请求示例

### 4.1 拉取接口调用（外部应用 → 本系统）

以按 id 拉取接口 `GET /open/api/sync/pull/by-id` 为例：

1. 业务 query 参数：`dataType=USER`、`bizIds=1,2,3`。
2. 签名字段（后续以请求头携带，不放 URL）：

   ```text
   appKey=<AccessKey>
   signMethod=HMAC_SHA256
   ts=1700000000000
   nonce=3f2a1b9c4e7d4f9a8b6c1d2e3f4a5b6c
   ```

3. 规范化拼接（业务参数 + 签名字段，按 key 升序，不含 `signature`）：

   ```text
   appKey=xxx&bizIds=1,2,3&dataType=USER&nonce=3f2a1b9c4e7d4f9a8b6c1d2e3f4a5b6c&signMethod=HMAC_SHA256&ts=1700000000000
   ```

4. 用 SecretKey 对上述字符串计算 HMAC-SHA256，得到 64 位十六进制 `signature`。
5. 最终请求（业务参数留在 URL query，5 个签名字段全部放请求头）：

   ```http
   GET /open/api/sync/pull/by-id?dataType=USER&bizIds=1,2,3
   appKey: xxx
   signMethod: HMAC_SHA256
   ts: 1700000000000
   nonce: 3f2a1b9c4e7d4f9a8b6c1d2e3f4a5b6c
   signature: <64位十六进制>
   ```

### 4.2 通知回调请求（本系统 → 外部应用）

外部应用需要在自己的回调接口中，按同样规则对收到的请求执行验签（详见第 5 节），核对
`appKey` 头对应的 AccessKey/SecretKey 是本系统颁发给自己应用的那一份。

```http
POST {notifyUrl}
appKey: xxx
signMethod: HMAC_SM3
ts: 1700000000000
nonce: xxx
signature: <128位十六进制>
Content-Type: application/json;charset=UTF-8

{"sequence":100,"dataType":"USER","operationType":"UPDATE","bizId":1,"occurredAt":"2026-08-17T10:00:00","extra":{}}
```

通知请求体只包含变更"指针"信息（序列号、数据类型、操作类型、对象 id、发生时间），不包含
完整业务数据；外部应用收到通知后，应主动调用拉取接口（4.1）获取真正的数据内容。

## 5. 校验规则

接收方（拉取接口的服务端 / 通知回调的外部应用）按以下顺序校验，任一环节失败均应拒绝请求：

1. **AccessKey 有效性**：`appKey` 请求头必须存在，且能定位到一个已启用的应用；
   Key 不存在与应用被停用应返回相同的错误提示，不区分具体原因，避免信息泄露。
2. **签名方法一致性**：`signMethod` 请求头必须与该应用当前配置的 `signAlgorithm` 对应的
   取值一致（`SHA256` → `HMAC_SHA256`，`SM3` → `HMAC_SM3`），不一致直接拒绝。
3. **时间戳有效期**：`ts` 请求头与当前系统时间之差的绝对值不能超过 **5 分钟**
   （300000 毫秒），超出视为过期请求。调用方应保证本地时钟与服务端时钟基本同步（NTP）。
4. **nonce 防重放**：`accessKey + nonce` 组合在时间戳有效期窗口内只能被消费一次，重复出现
   视为重放攻击并拒绝。
5. **签名比对**：按第 3 节规则重新计算签名，与请求头 `signature` 做**不区分大小写**的
   字符串比较，一致才通过。

以上校验仅在该应用 `needSign=true` 时执行；`needSign=false` 时仍需携带 `appKey`
请求头以定位调用方应用，但跳过签名校验。

## 6. 错误响应

校验失败统一返回 HTTP 200 + 业务状态码 `401`（本系统响应体结构为
`{ code, message, data }`，`code` 非 0 表示失败）：

```json
{
  "code": 401,
  "message": "签名校验失败",
  "data": null
}
```

可能的 `message` 取值包括：

- `缺少 appKey 请求头`
- `应用不存在或已停用`
- `签名校验失败`（签名方法不一致 / 时间戳过期 / nonce 重放 / 签名比对不通过，统一提示，
  不区分具体原因）

## 7. 安全注意事项

- SecretKey 只在管理端「重置 SecretKey」接口的响应中出现一次明文，其余任何查询接口都
  不会返回明文，外部应用需要在本地安全存储（如密钥管理服务/加密配置），不要写入日志或
  提交到代码仓库。
- 建议所有对接接口统一使用 HTTPS 传输，签名机制防的是参数篡改和重放，不能替代传输层加密。
- `nonce` 建议使用不含分隔符的 UUID（如 `UUID.randomUUID().toString().replace("-", "")`），
  保证足够的随机性，避免可预测导致的重放风险。
- 服务端 nonce 去重目前是单进程内存实现，多实例部署场景下同一 nonce 可能在不同实例上各自
  被判定为"首次出现"而放行两次，属于已知限制，外部应用侧不应仅依赖服务端防重放，业务上
  也应做好幂等处理（如以 `sequence`/`bizId` 去重）。

## 8. Java 签名示例代码

以下两个示例均只依赖 JDK 标准库（`java.net.http.HttpClient` + `javax.crypto.Mac`，
Java 11+），实现的是 `HMAC_SHA256` 签名方法，可直接整段复制到应用工程中，替换
`ACCESS_KEY`/`SECRET_KEY`/`BASE_URL` 后使用。若应用对接的接口 `signAlgorithm` 配置为
`SM3`，需要自行引入国密算法库（如 `bouncycastle`，本系统服务端就是用它实现 HMAC-SM3 的，
见 `SignAlgorithmCodecImpl`）替换示例中的 `hmac` 方法，`signMethod` 相应改为
`HMAC_SM3`，其余逻辑不变。

### 8.1 GET 请求签名示例（调用拉取接口）

对应第 4.1 节，调用本系统对外拉取接口 `GET /open/api/sync/pull/by-id`：业务参数留在 URL
query，5 个签名字段通过请求头携带。

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.TreeMap;
import java.util.UUID;
import java.util.stream.Collectors;
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;

/**
 * GET 请求签名示例：调用本系统对外拉取接口 /open/api/sync/pull/by-id。
 * 业务参数放 URL query，appKey/signMethod/ts/nonce/signature 5 个签名字段放请求头。
 */
public class GetSignExample {

    private static final String BASE_URL = "http://localhost:48080";
    private static final String ACCESS_KEY = "替换为分配给你应用的 AccessKey";
    private static final String SECRET_KEY = "替换为分配给你应用的 SecretKey";
    private static final String SIGN_METHOD = "HMAC_SHA256";
    private static final String HMAC_SHA256_ALGORITHM = "HmacSHA256";

    public static void main(String[] args) throws Exception {
        // 1. 业务 query 参数（按接口实际需要替换）
        Map<String, String> queryParams = new LinkedHashMap<>();
        queryParams.put("dataType", "USER");
        queryParams.put("bizIds", "1,2,3");

        // 2. 签名字段（参与签名，但最终放请求头，不放 URL）
        String ts = String.valueOf(System.currentTimeMillis());
        String nonce = UUID.randomUUID().toString().replace("-", "");
        Map<String, String> signFields = new LinkedHashMap<>();
        signFields.put("appKey", ACCESS_KEY);
        signFields.put("signMethod", SIGN_METHOD);
        signFields.put("ts", ts);
        signFields.put("nonce", nonce);

        // 3. 规范化拼接 = 业务 query 参数 + 签名字段，按 key 升序拼接后计算签名
        Map<String, String> canonicalizeInput = new LinkedHashMap<>(queryParams);
        canonicalizeInput.putAll(signFields);
        String signature = hmac(SECRET_KEY, canonicalize(canonicalizeInput));

        // 4. 拼接 URL（仅业务参数）并发起请求，签名字段通过请求头携带
        String url = BASE_URL + "/open/api/sync/pull/by-id?" + toQueryString(queryParams);
        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(url))
                .header("appKey", ACCESS_KEY)
                .header("signMethod", SIGN_METHOD)
                .header("ts", ts)
                .header("nonce", nonce)
                .header("signature", signature)
                .GET()
                .build();

        HttpResponse<String> response = HttpClient.newHttpClient()
                .send(request, HttpResponse.BodyHandlers.ofString());
        System.out.println("status=" + response.statusCode());
        System.out.println("body=" + response.body());
    }

    /** 把参数 Map 按 key 的 ASCII 升序拼接为 k1=v1&k2=v2&...，值不做二次编码。 */
    private static String canonicalize(Map<String, String> params) {
        return new TreeMap<>(params).entrySet().stream()
                .map(e -> e.getKey() + "=" + e.getValue())
                .collect(Collectors.joining("&"));
    }

    /** 计算 HMAC-SHA256，返回小写十六进制字符串。 */
    private static String hmac(String secretKey, String content) throws Exception {
        Mac mac = Mac.getInstance(HMAC_SHA256_ALGORITHM);
        mac.init(new SecretKeySpec(secretKey.getBytes(StandardCharsets.UTF_8), HMAC_SHA256_ALGORITHM));
        byte[] digest = mac.doFinal(content.getBytes(StandardCharsets.UTF_8));
        return HexFormat.of().formatHex(digest);
    }

    /** 把参数 Map 编码为 URL query 字符串，仅用于业务参数。 */
    private static String toQueryString(Map<String, String> params) {
        return params.entrySet().stream()
                .map(e -> e.getKey() + "=" + URLEncoder.encode(e.getValue(), StandardCharsets.UTF_8))
                .collect(Collectors.joining("&"));
    }
}
```

### 8.2 POST 请求签名示例（携带请求体的签名）

对应第 3.4 节"通知回调请求"签名规则（URL 签名 + body 签名拼接，共 128 位十六进制字符）。
本系统向外部应用发起通知回调时就是按此规则签名的（见 `NotifySignatureAppender`），若应用
需要以同一套规则向其他也遵循本规范的 POST 接口发起签名请求，可参考以下代码：5 个签名字段
全部通过请求头携带，不出现在 URL 上。

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.TreeMap;
import java.util.UUID;
import java.util.stream.Collectors;
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;

/**
 * POST 请求签名示例：携带 JSON 请求体的签名请求，URL 签名 + body 签名拼接，
 * appKey/signMethod/ts/nonce/signature 5 个签名字段全部放请求头。
 */
public class PostSignExample {

    private static final String TARGET_URL = "http://localhost:8080/your/callback/endpoint";
    private static final String ACCESS_KEY = "替换为分配给你应用的 AccessKey";
    private static final String SECRET_KEY = "替换为分配给你应用的 SecretKey";
    private static final String SIGN_METHOD = "HMAC_SHA256";
    private static final String HMAC_SHA256_ALGORITHM = "HmacSHA256";

    public static void main(String[] args) throws Exception {
        // 1. 请求体原始 JSON 字符串（按接口实际需要替换，注意签名与实际发送必须使用同一份原文）
        String requestBody = "{\"sequence\":100,\"dataType\":\"USER\",\"operationType\":\"UPDATE\",\"bizId\":1}";

        // 2. 仅 4 个签名字段参与 URL 签名（不含业务参数，通知回调请求本身不带业务 query 参数）
        String ts = String.valueOf(System.currentTimeMillis());
        String nonce = UUID.randomUUID().toString().replace("-", "");
        Map<String, String> signFields = new LinkedHashMap<>();
        signFields.put("appKey", ACCESS_KEY);
        signFields.put("signMethod", SIGN_METHOD);
        signFields.put("ts", ts);
        signFields.put("nonce", nonce);

        // 3. urlSign + bodySign 拼接为最终 signature（128 位十六进制字符，无分隔符）
        String urlSign = hmac(SECRET_KEY, canonicalize(signFields));
        String bodySign = hmac(SECRET_KEY, requestBody);
        String signature = urlSign + bodySign;

        // 4. 发起 POST 请求，5 个签名字段全部放请求头，URL 保持目标地址原样
        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(TARGET_URL))
                .header("appKey", ACCESS_KEY)
                .header("signMethod", SIGN_METHOD)
                .header("ts", ts)
                .header("nonce", nonce)
                .header("signature", signature)
                .header("Content-Type", "application/json;charset=UTF-8")
                .POST(HttpRequest.BodyPublishers.ofString(requestBody, StandardCharsets.UTF_8))
                .build();

        HttpResponse<String> response = HttpClient.newHttpClient()
                .send(request, HttpResponse.BodyHandlers.ofString());
        System.out.println("status=" + response.statusCode());
        System.out.println("body=" + response.body());
    }

    /** 把参数 Map 按 key 的 ASCII 升序拼接为 k1=v1&k2=v2&...，值不做二次编码。 */
    private static String canonicalize(Map<String, String> params) {
        return new TreeMap<>(params).entrySet().stream()
                .map(e -> e.getKey() + "=" + e.getValue())
                .collect(Collectors.joining("&"));
    }

    /** 计算 HMAC-SHA256，返回小写十六进制字符串。 */
    private static String hmac(String secretKey, String content) throws Exception {
        Mac mac = Mac.getInstance(HMAC_SHA256_ALGORITHM);
        mac.init(new SecretKeySpec(secretKey.getBytes(StandardCharsets.UTF_8), HMAC_SHA256_ALGORITHM));
        byte[] digest = mac.doFinal(content.getBytes(StandardCharsets.UTF_8));
        return HexFormat.of().formatHex(digest);
    }
}
```
