# 插件设计说明

本文档说明插件包升级功能（`openspec/changes/plugin-jar-upgrade`）的插件加载流程与核心实现，供后续维护/排查问题、以及插件开发方参考。完整的需求背景、技术决策取舍、行为契约请分别参见该 change 目录下的 `proposal.md`、`design.md`、`specs/plugin-jar-management/spec.md`、`specs/plugin-bean-override/spec.md`；本文档是对已落地代码的实现说明，不是规划性文档。

## 总体流程

整个插件加载发生在主程序**唯一一次** `ApplicationContext.refresh()` 内、Spring 处理完主程序自身 `@ComponentScan` 产生的 Bean 定义之后、任何 Bean 开始实例化之前。入口是 `cn.nihility.rbac.plugin.support.PluginBeanDefinitionRegistrar`。

```
主程序 @ComponentScan 完成
        │
        ▼
PluginBeanDefinitionRegistrar.postProcessBeanDefinitionRegistry(registry)
        │
        ├─ 1. 绑定 rbac.plugin.* 配置（bindProperties）
        ├─ 2. PluginJarScanner.scan(目录)           → 枚举 plugins/ 下 .jar，按文件名排序
        ├─ 3. 逐个 readMetadata(jar)                → 读 META-INF/plugin.properties
        ├─ 4. 按 priority(升序)/文件名 重新排序候选
        ├─ 5. seedMainProgramPaths(registry, ...)   → 把主程序已有 Controller 路径登记为基线
        └─ 6. 对每个候选插件调用 processPlugin(...)
                  │
                  ├─ 6a. PluginClassLoaderFactory.create()   → 建插件专属 URLClassLoader
                  ├─ 6b. PluginComponentScanner.scan()       → 枚举 jar 内 @Component 系候选类
                  │      （6a/6b 任一失败 ⇒ 整个插件标记 FAILED，不注册任何 Bean 定义）
                  └─ 6c. 逐个候选类调用 registerComponent()
                            │
                            ├─ 声明了 @PluginOverride → registerOverride()
                            └─ 未声明                 → registerNewBean()
```

## 重点类与方法

**`PluginJarScanner.scan(Path directory)`**

只做"发现"：目录不存在/不是目录 → 记日志、返回空列表（不影响主程序启动）；否则枚举 `.jar` 文件，忽略子目录和非 jar 文件，按文件名字典序返回。真正的处理顺序（结合 `priority`）在 Registrar 里重排。

**`PluginMetadataReader.read(JarFile, Path)`**

读插件 jar 内 `META-INF/plugin.properties`（`name`/`version`/`priority`，均可选）。文件缺失、属性缺失、`priority` 不是合法整数，都只记警告用兜底值（文件名/`UNKNOWN`/默认优先级），不算加载失败——元信息缺失本身不该让插件加载不了。

**`PluginClassLoaderFactory.create(jarPath, pluginName, parentLoader)`**

为每个插件建一个专属 `URLClassLoader`，`parent` 是主程序类加载器。利用 `URLClassLoader` 默认就是 parent-first 委派这个特性：先找主程序/Spring 已有的类，找不到才在插件自己的 jar 里找，天然保证公共类只加载一次、插件私有类被正确隔离加载。

**`PluginComponentScanner.scan(jarPath, pluginClassLoader)`**

这里有一处对 design.md 原方案的工程调整：原方案打算用 Spring 的 `ClassPathScanningCandidateComponentProvider`，但它基于 `classpath*:` 扫描资源，在 parent-first 的 `URLClassLoader` 下会把主程序自身及全部依赖 jar 里的类也扫进来，不符合"只扫插件自身"的要求。所以改成直接遍历该 jar 的 `JarEntry`，用 `Class.forName(name, false, pluginClassLoader)`（`initialize=false`，不触发静态初始化）逐个加载，再用 `AnnotatedElementUtils.hasAnnotation(clazz, Component.class)` 判断是否是 `@Controller`/`@RestController`/`@Service`/`@Component`/`@Configuration`（这些都是 `@Component` 的元注解，一次判断全覆盖）。

**`PluginBeanDefinitionRegistrar`（核心编排者）**

- `getOrder()` 返回 `Ordered.LOWEST_PRECEDENCE`。这里也有一处对 design.md 的调整：原描述是"返回一个数值大于 `ConfigurationClassPostProcessor` 的值"，但后者自身就返回 `LOWEST_PRECEDENCE`（已经是最大值）。类注释里解释了真正起作用的其实是"发现时机"——`ConfigurationClassPostProcessor` 是容器预注册的固定 Bean，第一轮 `PriorityOrdered` 扫描唯一能找到的候选者，它跑完才会处理完主程序的 `@ComponentScan`；本类作为 `cn.nihility.rbac` 包内的 `@Component`，本身要等那一轮跑完才"存在"，所以天然只能在后续批次被调用，效果等价于"晚于主程序组件扫描"。
- `registerOverride(...)`：按 `@PluginOverride(target=X.class)` 用 `beanFactory.getBeanNamesForType(targetType, ...)` 定位主程序里唯一匹配的 bean name（找不到/有多个候选都判定该类失败），先查 `OverrideDenyListChecker` 黑名单，通过后用**同一个 bean name** 重新 `registerBeanDefinition`（依赖 `spring.main.allow-bean-definition-overriding: true`）。多个插件覆盖同一目标时，`overrideOwners` 这个 `Map` 记录"当前生效者"，被顶替时记一条冲突到 `PluginRegistry`。
- `registerNewBean(...)`：未声明覆盖的类用 `plugin.<pluginName>.<SimpleClassName>` 命名空间前缀生成 bean name；如果是 Controller，先用 `RequestMappingPathResolver.resolvePaths(clazz)` 反射读出它的请求路径，拿去 `ControllerPathRegistry.tryRegister(...)` 和"已知路径集合"（主程序 + 已处理插件）比对，冲突就直接不注册这个类（避免留到运行期 `RequestMappingHandlerMapping` 初始化时才炸出 "Ambiguous mapping"）。

**`RequestMappingPathResolver.resolvePaths(Class<?>)`**

用 `AnnotatedElementUtils.findMergedAnnotation` 合并解析类级 + 方法级 `@RequestMapping`（`@GetMapping` 等快捷注解通过 `@AliasFor` 被一并覆盖），拼出规范化后的完整路径集合。这是"尽量在定义阶段提前发现冲突"的静态最佳努力实现，不追求和运行期完全等价（比如不看 HTTP method、请求头条件这些）。

## 失败隔离的边界

这是这次改动的关键取舍，直接体现在代码结构上：

- `processPlugin()` 里，"建类加载器 + 扫描组件"这一步用 try/catch 包成一个整体——失败就整个插件 `FAILED`，一个 Bean 定义都不注册。
- 逐个候选类调用 `registerComponent()` 时是**类粒度**的 try/catch——单个类注册失败（覆盖目标找不到、命中黑名单、路径冲突）只是这个类被跳过（记进 `PluginInfo.skippedClasses`），插件整体仍是 `REGISTERED`，其他类正常注册。
- 以上都停留在"Bean 定义注册"这个阶段。一旦定义注册完，真正的实例化（构造器/`@PostConstruct`）和主程序自身 Bean 混在同一批里跑，插件 Bean 这时候抛异常就是整个 `refresh()` 失败、主程序启动不了——这是本次明确接受、没有再包一层的行为，`PluginBeanDefinitionRegistrarIntegrationTest#pluginBeanInstantiationFailure_shouldFailWholeContextStartup` 这个测试验证的就是"这确实会导致整体失败"，而不是"被隔离恢复"。

## 查询侧

`PluginRegistry`（内存态登记表，作为普通单例在 `postProcessBeanDefinitionRegistry` 一开始就用 `beanFactory.registerSingleton` 注册进容器）收集每个插件的 `PluginInfo`（状态、失败原因、覆盖关系、跳过的类）和跨插件的覆盖冲突记录；`PluginQueryServiceImpl` 从中读数据组装成 `PluginListVO`；`PluginController#list()` 通过 `GET /api/v1/plugins` 暴露出去，权限走项目现成的 `menu` 请求头机制（`PluginManagement:plugin:view`），Controller 本身不用写权限判断代码。
