## Purpose

以组织为导航维度的任职记录独立管理能力：按所属组织分页查询任职记录、任职记录详情查询、创建、更新、启用/停用、逻辑删除，以及配套的前端"组织树（懒加载）+ 任职记录分页表格"的主从式管理界面。复用用户管理模块既有的 `tab_user_position` 表/实体/Mapper，是身份管理体系（组织 → 用户 → 角色 → 权限）中"任职关系"维度独立于 `user-management` 内嵌子表单之外的另一个管理入口，依赖 `org-management` 提供组织树数据、`user-management` 提供用户数据、`dict-management` 提供"任职类型"字典数据。

## Requirements

### Requirement: 任职记录按组织分页查询
系统 SHALL 提供按所属组织 id 分页查询任职记录的接口，`orgId` 为必填参数（不存在"顶级组织聚合查询"的语义）；分页参数 `page`（默认 `1`）、`pageSize`（默认 `10`）均为可选；仅返回未被逻辑删除（`status != -1000`）的任职记录，每条记录包含所属用户 id 及姓名、所属组织 id 及名称、任职类型编码、任职地址、任职电话、显示序号、备注、状态；结果按 `showOrder` 降序、相同时按 `id` 升序排列。

#### Scenario: 查询指定组织下的任职记录
- **WHEN** 客户端调用 `GET /api/positions?orgId={id}&page={page}&pageSize={pageSize}`
- **THEN** 系统返回 `orgId` 等于该 id 的未删除任职记录分页结果，包含 `records`（含 `userName`、`orgName`）、`total`、`page`、`pageSize`

#### Scenario: 未指定 orgId 时拒绝查询
- **WHEN** 客户端调用 `GET /api/positions` 且未携带 `orgId` 参数
- **THEN** 系统返回业务错误（非零 `code`），不做默认聚合查询

#### Scenario: 未指定分页参数时使用默认值
- **WHEN** 客户端调用 `GET /api/positions?orgId={id}` 且未携带 `page`、`pageSize` 参数
- **THEN** 系统按 `page = 1`、`pageSize = 10` 处理

#### Scenario: 已逻辑删除的任职记录不出现在查询结果中
- **WHEN** 某条任职记录的 `status` 为 `-1000`
- **THEN** 该条记录不出现在 `GET /api/positions` 的返回结果中

### Requirement: 任职记录详情查询
系统 SHALL 提供按 id 查询任职记录详情的接口，返回结果包含所属用户 id 及姓名、所属组织 id 及名称、任职类型编码、任职地址、任职电话、显示序号、备注、状态，以及创建人、创建时间、更新人、更新时间。

#### Scenario: 查询存在的任职记录
- **WHEN** 客户端调用 `GET /api/positions/{id}` 且该记录存在且未被逻辑删除
- **THEN** 系统返回该任职记录的完整信息

#### Scenario: 查询不存在的任职记录
- **WHEN** 客户端调用 `GET /api/positions/{id}` 且该 id 不存在或已被逻辑删除
- **THEN** 系统返回业务错误（非零 `code`），不返回 HTTP 500

### Requirement: 新增任职记录
系统 SHALL 支持独立创建任职记录，所属用户 id（`userId`）、所属组织 id（`orgId`）、任职类型编码（`positionType`）为必填项；任职地址、任职电话、备注为可选字段；显示序号默认 `0`。新建任职记录默认状态为启用（`2000`）。

#### Scenario: 成功创建任职记录
- **WHEN** 客户端调用 `POST /api/positions`，携带合法的 `userId`、`orgId`、`positionType`
- **THEN** 系统创建该任职记录，状态为 `2000`（启用），并返回创建后的记录信息

#### Scenario: 必填字段缺失时拒绝创建
- **WHEN** 客户端调用 `POST /api/positions` 且未携带 `userId`、`orgId` 或 `positionType` 之一
- **THEN** 系统拒绝创建，返回参数校验错误

### Requirement: 更新任职记录
系统 SHALL 支持更新任职记录的所属组织、任职类型、任职地址、任职电话、显示序号、备注；不支持通过本接口修改所属用户（`userId`），也不修改状态。

#### Scenario: 成功更新任职记录
- **WHEN** 客户端调用 `PUT /api/positions/{id}`，携带合法的 `orgId`、`positionType` 等字段
- **THEN** 系统更新该任职记录信息并返回更新后的结果，`userId`、`status` 保持不变

#### Scenario: 更新接口不接受所属用户字段
- **WHEN** 客户端调用 `PUT /api/positions/{id}` 的请求体中不包含 `userId` 字段
- **THEN** 系统仅更新组织、任职类型等允许修改的字段，该记录的所属用户不发生变化

### Requirement: 任职记录启用与停用
系统 SHALL 提供独立的接口将任职记录状态切换为启用（`2000`）或停用（`3000`），与新增/更新接口分离。

#### Scenario: 启用任职记录
- **WHEN** 客户端调用 `PUT /api/positions/{id}/enable`
- **THEN** 系统将该任职记录 `status` 置为 `2000` 并返回更新后的记录信息

#### Scenario: 停用任职记录
- **WHEN** 客户端调用 `PUT /api/positions/{id}/disable`
- **THEN** 系统将该任职记录 `status` 置为 `3000` 并返回更新后的记录信息

### Requirement: 任职记录逻辑删除
系统 SHALL 支持对任职记录执行逻辑删除（将 `status` 置为 `-1000`），不做物理删除。

#### Scenario: 成功删除任职记录
- **WHEN** 客户端调用 `DELETE /api/positions/{id}`
- **THEN** 系统将该任职记录 `status` 置为 `-1000`，该记录此后不再出现在按组织分页查询、详情查询的结果中

### Requirement: 任职记录状态语义
系统 SHALL 使用统一的整型状态码表达任职记录的启停用与删除语义：`2000` 表示启用，`3000` 表示停用，`-1000` 表示已逻辑删除；三者互斥，与组织、用户模块的状态码含义保持一致。

#### Scenario: 状态码含义一致
- **WHEN** 系统返回任意任职记录的 `status` 字段
- **THEN** 其值必为 `2000`、`3000`、`-1000` 三者之一，分别代表启用、停用、已删除

### Requirement: 任职管理前端界面
系统 SHALL 提供任职管理页面（路径 `/identity/positions`），左侧展示组织树，右侧以分页表格展示当前选中组织下的任职记录。左侧组织树 SHALL 默认全部收起，采用与组织管理页面一致的懒加载方式逐层展开。未选中任何左侧树节点时，右侧 SHALL 展示空状态并提示用户先选择组织，不做默认聚合查询；用户点击左侧树的某个节点后，右侧按该组织 id 分页查询并展示任职记录（每页 10 条），列表列包含姓名、组织、任职类型、任职地址、任职电话、状态、显示序号，其中"姓名"列之后紧跟"组织"列，展示该条任职记录的组织名称（`orgName`）；该表格列表头使用精简文案"组织"，区别于新增/编辑弹窗与详情弹窗中"所属组织"这一完整字段标签。页面 SHALL 支持新增、编辑、启用、停用、删除、详情：

- 新增：通过下拉远程搜索选择一个已存在的用户，所属组织默认预填为左侧当前选中的组织节点（可修改为其他组织），填写任职类型（数据源为字典管理模块暴露的按 `position_type` 查询启用项接口）、任职地址、任职电话、显示序号、备注。
- 编辑：可修改所属组织、任职类型、任职地址、任职电话、显示序号、备注；所属用户以只读方式展示，不可修改。
- 启用/停用/删除：与组织管理、用户管理页面的交互模式一致（列表行内操作按钮 + 删除二次确认）。
- 详情：只读展示任职记录完整信息（含所属用户、所属组织、任职类型、任职地址、任职电话、显示序号、备注、状态、创建人、创建时间、更新人、更新时间）。

#### Scenario: 左侧组织树默认全部收起
- **WHEN** 用户打开任职管理页面
- **THEN** 左侧组织树的所有节点默认处于收起状态，不自动展开任何层级

#### Scenario: 点击展开节点时懒加载该层子节点
- **WHEN** 用户点击左侧组织树中某个尚未展开的节点的展开箭头
- **THEN** 系统调用组织树懒加载子节点查询接口获取该节点的直属子组织并渲染为下一层，不影响其他节点的展开状态

#### Scenario: 未选中组织节点时右侧为空状态
- **WHEN** 用户打开任职管理页面且尚未点击左侧树的任何节点
- **THEN** 右侧不展示任职记录表格数据，展示提示用户先选择左侧组织的空状态文案

#### Scenario: 选中组织节点后展示其任职记录
- **WHEN** 用户点击左侧组织树中的某个节点
- **THEN** 右侧表格按该组织 id 分页查询并展示任职记录（重置为第一页），列出姓名、组织、任职类型、任职地址、任职电话、状态、显示序号

#### Scenario: 姓名列后紧跟组织列
- **WHEN** 用户查看右侧任职记录表格
- **THEN** "姓名"列（展示 `userName`）紧接着的下一列是"组织"列（展示 `orgName`），表头文案是精简的"组织"而不是"所属人员"或"所属组织"

#### Scenario: 新增任职记录时选择已存在用户
- **WHEN** 用户在已选中某个组织节点的情况下点击"新增"，在弹窗的用户选择框中输入姓名关键字进行远程搜索并选中一个用户
- **THEN** 新增表单记录该用户为所属用户，所属组织默认预填为当前选中的组织节点（用户仍可手动改选为其他组织）

#### Scenario: 编辑任职记录时所属用户不可修改
- **WHEN** 用户对某条任职记录点击"编辑"
- **THEN** 弹窗中所属用户以只读方式展示，无法修改；所属组织、任职类型、任职地址、任职电话、显示序号、备注可编辑

#### Scenario: 列表操作触发的状态变更实时可见
- **WHEN** 用户在右侧表格中对某一行执行启用、停用或删除操作
- **THEN** 操作成功后表格当前页数据刷新以反映最新状态；若刷新后当前页码超出新的总页数，则自动回退到最后一页

#### Scenario: 查看任职记录详情
- **WHEN** 用户在右侧表格某一行点击"详情"
- **THEN** 系统以只读方式展示该任职记录的完整信息：所属用户、所属组织、任职类型、任职地址、任职电话、显示序号、备注、状态、创建人、创建时间、更新人、更新时间
