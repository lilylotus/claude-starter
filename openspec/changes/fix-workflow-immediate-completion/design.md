## Context

用户报告 ADD_USER 新增用户在性别为空或非女时无待办、无新增结果。静态证据：FlowableWorkflowService.start 启动并回填引擎 ID 后直接返回，未调用 finalizeInstanceIfEnded；后者目前在任务操作后使用。WorkflowV2EndOutcomeListener 只写 approved 变量。ApprovalRequestServiceImpl.submit 固定返回 pending；业务落库仅由 approve 路径调用 finalizeApproval。frontend/src/utils/approvalResult.ts 对 approvalEnabled=true 固定提示等待且不刷新。

现有条件路由集成测试的默认分支仍然进入审批节点，未覆盖直接 END。实际 ADD_USER 已发布 DSL、绑定版本、实例历史尚未读取，因此目前结论为代码缺陷与报告现象吻合，不能宣称已复现现场数据。

## Goals / Non-Goals

**Goals:**
- 修复启动即通过时申请、流程与业务状态不同步的问题。
- 保留直接拒绝、系统终止和实际运行中分支的正确语义。
- 自动通过执行现有业务权限、范围及业务规则校验，保持事务与锁收尾一致。
- 返回和展示实际结果，覆盖女、非女、空性别的条件分支。

**Non-Goals:**
- 不硬编码性别条件，不修改已有模型路由或新增审批人。
- 不扩展定时器、异步任务的全局终态协调架构，不新增依赖或数据库迁移。
- 不自动补执行历史悬挂申请。

## Decisions

### 1. 在流程启动的命令边界同步终态

引擎启动完成后以最新投影为准回填引擎 ID，避免用启动前的 RUNNING 对象覆盖监听器产生的节点信息或 TERMINATED 状态。复用并增强 finalizeInstanceIfEnded：保留已存在的终止等终态，只对符合条件的运行中实例检查引擎是否结束，按历史 approved 变量区分通过/拒绝。仍有引擎执行（包括未来异步等待）时保持运行中，不能仅以无人工任务判定通过。

不采用单独在 END 监听器里执行业务写入，因为该时刻上层申请尚未完成流程关联，且会把业务层耦合进引擎回调。

### 2. 申请提交关联完成后按实际状态收尾

submit 保存申请与流程关联后读取实际流程状态：RUNNING 保留待审批；APPROVED 复用现有业务执行逻辑，更新申请、resultTargetId、审计和释放业务锁；REJECTED/TERMINATED 更新拒绝结果及原因、释放锁且不执行业务。通过与拒绝收尾保持在现有事务内，避免重复执行。自动审批记录明确系统自动处理，审批人可空，不伪造发起人人工同意；执行身份、更新人和审批人分别处理，CurrentUserContext 始终恢复调用前身份。

当前 finalizeApproval 为同步业务写入路径，沿用此实际行为；业务校验失败时整体回滚，包括申请、引擎状态和锁，不出现成功提示或部分业务写入。不另建绕过既有校验的 createUser 路径。

### 3. 保持审批参与标志并依据申请状态展示

approvalEnabled 继续表示进入审批流程；已自动结束仍返回关联申请及最新状态，避免把它改成 false 导致审计语义丢失。前端公共结果提示区分待审批、已通过和已拒绝，已通过提示生效并刷新列表，已拒绝说明未生效。现有关闭审批直接生效路径保持兼容。同步更新相关注释/API 描述，按实际实现决定是否需要结果工厂命名调整，不引入无必要字段。

## Risks / Trade-offs

- [实际模型默认出口可能为拒绝] → 以已发布 END outcome 为准，测试分别覆盖通过与拒绝，不把所有无待办情况强制放行。
- [终止状态被旧投影覆盖] → 启动后重新读取并最小化回填，增加终态保护测试。
- [自动路径重复执行或身份误记] → 复用单一收尾逻辑，断言一次写入、系统审批轨迹及上下文恢复。
- [历史申请修复涉及重放业务] → 发布不自动补写，后续按实例和业务记录核对后制定恢复步骤。
- [工作区含其他已暂存修改] → 不覆盖或撤销，按本次 diff 和测试更新文档。

## Migration Plan

确认后实现并运行定向回归、后端测试和前端构建。无需数据库迁移或重新发布流程模型。上线后验证新建女/非女/空性别请求；回退采用代码版本回退，不删除已经成功创建的业务记录。

## Open Questions

- 现场 ADD_USER 默认出口与绑定版本需在可访问运行环境时核实；若不可访问，报告模拟模型验证的边界。
- 历史悬挂申请数量与恢复需求尚未核验，不阻塞新请求链路修复。
