## Context

当前迁移目录包含旧的 46 表 `V1__init_schema.sql`，以及 V2–V14、V18–V20 共 16 个增量脚本；V15–V17 当前并不存在，合并时必须按实际文件集合与数值版本顺序处理，不能假设版本连续。增量链新增聊天域 5 张表、用户角色规则 4 张表、工作流引擎 8 张表、生产级审批生命周期 10 张表，共形成 73 张业务表的最终状态，并多次修改既有表字段及追加权限、菜单和审批种子。

项目已有多次基线合并实践，权威 spec 要求迁移目录保持可维护的单一基线，且一份脚本同时兼容 MySQL 5.7 和 8.0。此类合并会改变 V1 校验和并删除已执行版本，因此只能供空 schema 使用。工作区当前另有未跟踪的 `.claude/settings.local.json`，本 change 不触碰该文件；进行中的 `production-approval-lifecycle` change 是 V11–V20 的需求来源，本次只规整 SQL 文件，不改写其尚未完成的实现状态。

## Goals / Non-Goals

**Goals:**

- 用单一 V1 一步创建现有迁移链的最终 73 张业务表、索引、约束和全部最终种子数据。
- 直接表达最终字段、默认值、可空性和种子状态，不保留历史 `ALTER`、补授或回填过程。
- 在 MySQL 5.7 与 8.0 上证明旧链和新基线的 schema 及语义种子数据等价。
- 使迁移目录最终只保留 `V1__init_schema.sql`，并同步 OpenSpec 中的单基线契约。

**Non-Goals:**

- 不为已有数据的数据库提供原地升级、Flyway history 修复或数据保留方案。
- 不修改业务 Java/前端代码、接口、依赖、权限编码或菜单语义。
- 不把 Flowable 管理的 `ACT_*`/`FLW_*` 表纳入业务 Flyway 基线。
- 不借合并机会重命名表、列、索引，或修正超出旧迁移链终态的业务数据。

## Decisions

### Decision 1: 以实际 17 文件迁移集合生成新的空库 V1

实施前保存 V1–V14、V18–V20 的文件名、SHA-256 和只读副本，按数值版本顺序建立 legacy 路径。新的 V1 表示该 legacy 路径全部执行后的最终状态，完成后删除除 V1 外的 16 个脚本。V15–V17 不存在属于当前仓库事实，不创建占位文件，也不在合并来源中虚构这三个版本。

备选方案是新增 V21 或保留所有旧文件。该方案能兼容已有数据库，却无法让新环境只执行一个初始化脚本，不满足本次目标。

### Decision 2: 表结构按最终形态合并到所属 CREATE TABLE

把 V2 的 5 张聊天表、V4 的 4 张用户角色规则表、V7 的 8 张工作流引擎表和 V11 的 10 张生产审批表放入新 V1，使建表语句总数为 73。V3、V6、V7–V9、V11、V12、V14、V18、V19 的 `ALTER TABLE` 逐列折叠回相应原始建表定义，包括登录方式、管理员自动角色来源、审批实例关联、DSL v2/发布/表单/幂等/会签相关字段及索引。

合并只采用两版 MySQL 的共同语法子集，保留现有反引号、字符集、默认值和索引定义。所有新增表继续具备创建人、创建时间、更新人、更新时间四个审计字段。

备选方案是将增量 SQL 原样拼接在 V1 尾部。它虽减少编辑量，却仍保留中间形态和历史补丁，不能称为规整后的初始化脚本。

### Decision 3: 种子数据直接表达最终状态并按依赖排序

聊天敏感词、默认工作流模型/定义/节点规则、四类业务的全局流程绑定，以及 V2、V5、V10、V14、V20 增加的菜单和权限点直接合并到对应种子块。所有权限数据插入完成后，再执行一次 SUPER_ADMIN 对全部权限的全量授权，不保留各版本的分段补授语句。目标权限集合与 `权限资源.txt` 当前 145 个唯一编码逐项相等。

种子对比使用稳定业务键（例如权限/菜单/角色 code、流程 process_code + version、绑定业务维度、敏感词文本），忽略自增 id、`NOW()` 时间、SQL 执行顺序导致的无语义主键差异。V7 中先插流程定义、再回写模型 current_definition_id，以及 V13 通过当前定义生成全局绑定的引用关系，在新基线中仍须保持语义一致。

备选方案是保留所有补授和 `UPDATE`。这会让空库初始化依赖历史中间态，也容易掩盖插入顺序或最终默认值错误。

### Decision 4: 用双数据库版本、双路径做结构和数据等价验证

在 MySQL 5.7 和 MySQL 8.0 中各建立两个显式命名的隔离空 schema：legacy schema 执行保存的 17 文件旧链，baseline schema 仅执行新 V1。每个版本均比较：

- 表、列、数据类型、可空性、默认值、主键、索引和唯一/外键约束。
- 73 张业务表以及增量涉及的关键表/字段。
- 按稳定业务键归一化后的种子数据与引用关系。
- 145 个权限编码及 SUPER_ADMIN 的完整授权覆盖。
- `flyway_schema_history` 在 baseline 路径中只包含成功的 V1。

测试 schema 不得使用 `application.yml` 当前配置的业务 schema。只有在解析并复核连接主机、端口和 schema 名后才允许清理隔离 schema；某个 MySQL 版本不可用时，对应任务保持未完成并明确报告，而不是以静态检查冒充执行验证。

备选方案是只运行 Spring 上下文测试。该测试不能证明旧链与新基线等价，也不能覆盖两个 MySQL 版本的语法差异。

### Decision 5: 已执行旧迁移链的数据库不切换新基线

替换已执行的 V1 会改变校验和，删除后续版本也会改变迁移历史。对保留数据的数据库执行 `repair`、删除 `flyway_schema_history` 或直接替换脚本，均不能证明现有业务表正好处于新基线终态，并可能导致重复建表/插入或部分执行。因此已有数据环境继续使用匹配旧校验和的发布物；只有明确可丢弃数据的环境才能完整删除并重建 schema 后使用新 V1。

## Risks / Trade-offs

- [27 张新增表及多轮 ALTER 人工折叠可能漏列、索引或默认值] → 用 legacy/new 的 information_schema 全量差异对比作为主要验收。
- [权限和流程种子含动态 id，逐行比较会产生假差异] → 按稳定业务键及解析后的引用关系归一化比较，并单独校验 145 个权限及超级管理员覆盖。
- [V15–V17 版本缺口可能被误判为遗漏文件] → 在来源清单和 V1 文件头明确实际合并集合，仅以工作区存在的 17 个脚本为准。
- [MySQL 5.7/8.0 对默认值、保留字和索引元数据表示存在差异] → 使用共同语法，分别真实执行；比较时规范化等价的元数据表现，但不忽略语义差异。
- [进行中的审批 change 可能继续产生新迁移] → 实施开始时重新盘点目录；若迁移集合已变化，先更新 proposal/design/tasks 并重新确认范围。
- [新制品用于已有库会触发 Flyway 校验失败] → 在 V1 文件头、OpenSpec 和交付说明中显著声明空 schema 限制，不提供绕过命令。

## Migration Plan

1. 实施开始时重新盘点迁移文件并保存 legacy 文件清单、哈希和只读副本。
2. 建立结构与种子终态清单，将全部最终定义重写进 V1，再删除其余 16 个脚本。
3. 静态核对 73 张表、145 个权限编码、审计字段以及 MySQL 5.7 禁用语法。
4. 在 MySQL 5.7/8.0 隔离 schema 上执行 legacy/new 双路径并比较结构与种子数据。
5. 使用隔离 schema 运行 Spring 上下文测试和后端全量测试，再依据真实结果同步 OpenSpec 文档。

代码回滚通过 Git 恢复旧的 17 文件迁移集合。数据库不做原地回滚：用新 V1 创建的可重建环境若需回退，应删除该隔离/开发 schema 后使用旧迁移链重新创建。

## Open Questions

无。若实施开始前迁移目录新增或修改脚本，则视为范围变化，必须先更新本 change 并再次请求确认。

## Validation Results

- MySQL 5.7.40：legacy V1–V14、V18–V20 与新 V1 均成功执行；73 张表、908 列、272 条索引元数据、120 条约束元数据的比较均为零差异。
- MySQL 8.0.46：使用同一迁移集合重复双路径验证，表、列、索引和约束比较均为零差异。
- 两版本 legacy/new 的 20 个非空种子表行数一致；权限、菜单、角色、管理员角色、默认流程、节点规则和 20 条全局绑定按稳定业务键归一化后零差异。V5 两条历史分段授权的 `create_by/update_by` 从 `system` 统一为新基线全量授权使用的管理员 id 文本 `1`，不改变角色—权限关系或授权能力。
- 新 V1 静态检查结果为 73 条 `CREATE TABLE`、0 条 `ALTER TABLE`、145 个唯一权限编码和 1 条 SUPER_ADMIN 全量授权语句；未发现 CTE、窗口函数、`JSON_TABLE`、厂商专属 upsert 或 Flowable `ACT_*`/`FLW_*` 建表语句。
- 隔离 MySQL 8.0 schema 上的 `RbacApplicationTests` 通过，Flyway history 只有成功的 V1；后端全量测试实际执行 1310 项、23 项失败，根因是既有工作流实体在 MyBatis-Plus wrapper 中生成驼峰列名，而非本次 SQL 合并造成的 schema 差异。用户确认在保留该警告的情况下同步并归档。
