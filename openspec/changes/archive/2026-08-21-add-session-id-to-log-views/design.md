## Context

`tab_login_log` 和 `tab_sso_protocol_log` 均已在 `V3__add_login_and_sso_protocol_log_session_id.sql` 中拥有 `session_id` 列（存放 SSO 会话令牌的 SHA-256 摘要），两表已可通过该字段关联。历史 change `2026-08-21-add-sso-protocol-access-log` 的 `design.md` Decision 7 明确规定"不在表格列里展示会话ID，仅作为查询参数使用"。本次变更是对这一条历史决策的定向反转，范围仅限于两处前端表格新增一列、后端 VO 新增一个透传字段，不涉及新的接口、新的数据库字段或新的查询能力。

## Goals / Non-Goals

**Goals:**
- 登录日志表格展示会话ID列。
- SSO 协议调用记录弹窗表格展示会话ID列。
- 延续摘要值（非原始令牌）的展示口径，不引入新的敏感信息暴露。

**Non-Goals:**
- 不改变登录日志 → 协议调用记录的下钻交互方式（继续用按钮 + 弹窗，不改行内展开）。
- 不新增查询参数或修改现有接口签名。
- 不新建独立的协议调用记录管理页面/菜单。
- 不涉及 `tab_login_log`、`tab_sso_protocol_log` 的表结构变更（字段已存在）。

## Decisions

- **反转 Decision 7（展示会话ID）**：原决策的顾虑是"管理员不需要看到哈希值本身"。展示 SHA-256 摘要不会泄露可用于冒充登录的原始凭据（这一点在原 Decision 6 中已论证过，本次予以延续），因此展示层面的顾虑不成立；而实际使用中管理员需要手动核对/复制会话标识，隐藏它反而增加操作成本。故本次让两侧表格都展示该字段，不做脱敏截断（脱敏截断会削弱"核对/复制"这个使用场景的价值，且摘要本身已不可逆，无需二次脱敏）。
- **会话标识长度由 64 位缩短为 32 位十六进制字符**：原 `SsoSessionIdHasher` 落存完整 SHA-256 摘要（64 位十六进制），在表格列里展示偏长、不利于阅读与核对。改为只截取摘要前 16 字节（128 位，32 位十六进制字符串）。128 位熵仍远超日志表实际可能出现的并发会话数量级，碰撞概率可忽略不计，不削弱"同一令牌产生同一标识、用于关联查询"的用途；`tab_login_log`/`tab_sso_protocol_log` 的 `session_id` 列定义为 `VARCHAR(64)`，缩短后的值天然兼容，无需数据库迁移。此调整只影响本次变更之后新产生的会话标识；变更上线前已落库的 64 位摘要记录保持原样，不做回填/迁移，二者共存于同一列不影响各自的关联查询（同一条记录的登录日志与协议调用记录仍用写入时刻算出的同一个值关联）。
- **仅扩展 VO，不改查询参数**：`SsoProtocolLogQueryRequest` 已支持 `sessionId` 精确匹配（用于弹窗内部请求),本次只需让 `SsoProtocolLogVO` 把已经查到的 `sessionId` 透传给前端展示，无需新增任何查询能力。
- **不改动 MapStruct 显式映射范围之外的逻辑**：`SsoProtocolLogConvert` 若逐字段声明了 VO 映射，只需要新增一行 `sessionId` 映射（或确认字段同名同类型时自动映射生效）；不重构该转换器的其余部分。

## Risks / Trade-offs

- [展示摘要值可能被误认为是可用的会话令牌，引发员工误操作（如把它当凭据分享）] → 前端在列头/tooltip 中注明"会话标识（摘要值，不可用于登录）"，降低误解风险。
- [协议调用记录弹窗新增一列可能在窄屏下挤压现有列的可读性] → 复用已有的响应式表格样式（`el-table` 默认横向滚动），不额外做特殊布局处理，保持改动最小。

## Migration Plan

无需数据库迁移（字段已存在）、无需灰度或回滚步骤；前后端各自随常规发布节奏上线即可。若需要回滚，直接回退相关前端组件与 VO 字段改动即可，不影响已落库数据。
