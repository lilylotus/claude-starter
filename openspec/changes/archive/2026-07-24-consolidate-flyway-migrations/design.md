## Context

项目early阶段每加一个字段、每修一个数据问题都新开一个 Flyway 版本文件，34 个版本里有
不少是"建表后马上又改"的连续动作（如 `V5` 建 `tab_user`/`tab_user_position`，`V6` 紧接着给
`tab_user_position` 加一列；`V18` 建 `tab_metadata_field`，`V24` 又给它加一列；`V32`/`V34`
分别把 `tab_user.gender`、`tab_form_field_definition` 的字典类型引用列从"原始值/id"改造成
"字典编码"）。这些文件本身没有被任何已上线环境依赖（项目仍处于本地开发阶段，未见生产部署
记录），继续保留只会让"这张表现在到底长什么样"这个问题需要跨若干个文件拼凑答案。

## Goals / Non-Goals

**Goals:**
- 迁移目录只保留一份反映当前最终 schema + 种子数据状态的基线文件。
- 合并过程不引入任何语义差异（列、索引、注释、种子数据的值都要和旧 34 个文件按顺序执行后的
  最终状态完全一致）。

**Non-Goals:**
- 不处理生产环境或任何已经执行过旧版本迁移的库的升级路径——本次改动假定使用方清空库后
  重新执行新基线（详见 proposal.md「Impact」）。
- 不改变任何业务代码、接口行为，纯粹是迁移文件的组织方式调整。

## Decisions

- **合并为单个 `V1__init_schema.sql`，而不是分模块合并成几个基线文件**：项目当前所有表
  之间存在种子数据的相互引用（如 `tab_menu` 种子数据引用其他模块的资源编码），拆成多个文件
  之间还要维护彼此的版本号先后顺序，不如单文件里按"先建表、后插入有依赖关系的种子数据"的
  顺序线性组织，依赖关系一目了然。
- **版本号使用 `V1`（而不是接着旧编号往后延，例如 `V35`）**：`V1` 代表"从零开始建库的基线"，
  语义上比延续一个已经不存在的历史编号更清楚；代价是旧版本号 `V1~V34` 不能再复用，任何还在
  用旧版本号跑过 migrate 的库必须清库重来（已在 proposal.md「Impact」中说明）。
- **不保留任何 `ALTER`/`UPDATE` 中间步骤**：例如不再"先建 `tab_user.gender` 为原始文本列，
  再一条 `UPDATE` 转成字典编码"，而是直接把该列定义为字典编码列、种子数据直接写最终值。
  好处是新环境执行链路更短；代价是丢失了"这个字段是什么时候、因为什么原因从 A 形态改成 B
  形态"的迁移历史，这部分历史仍可通过 git 提交记录（本次合并对应的历史 commit）追溯。

## Migration Plan

1. 逐表、逐条种子数据把旧 `V1~V34` 按版本号顺序应用后的最终状态整理进 `V1__init_schema.sql`
   （已完成，详见验证记录）。
2. 删除旧 `V1__init_tab_org.sql` 到 `V34__convert_form_field_dict_type_id_to_code.sql`（已完成，
   `git rm`，历史可追溯）。
3. 本地/测试库需清空或删除 `flyway_schema_history` 表后重新执行新 `V1`（文件头部注释已写明）。
4. 无回滚计划——如需回退，`git revert` 本次改动对应的 commit 即可恢复旧的 34 个文件。
