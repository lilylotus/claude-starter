## Context

`UserManagementView.vue` 的任职信息子表单里，"所属组织""认证类型"两个字段各自通过独立的 `label-width="76px"`（区别于表单外层的 `label-width="90px"`）与 `:rules` 挂载必填校验。Element Plus 在字段 `required` 时会给 `.el-form-item__label` 前面加一个红色 `*`，这会占用一小段额外宽度；`所属组织`/`认证类型` 都是 4 个汉字，在 76px 的标签宽度下，星号挤占的空间不够，触发标签换行，导致该行（`grid-template-columns: 1fr 1fr` 的两列）高度被撑高且左右不对齐。项目里另外三处表单（`OrgManagementView.vue`、`DictManagementView.vue` 及本页外层用户主表单）用的都是 `90px`，同样是 4 字标签 + 必填星号，没有出现换行问题，说明 `90px` 是本项目已验证可行的惯例值。

同时，该子表单和详情表格里的"认证类型"字段标签，实际语义是任职关系的类型（主职/兼职/挂职），沿用字典类型名字"认证类型"容易被用户误解为身份认证配置，需要改为语义更准确的"任职类型"。

## Goals / Non-Goals

**Goals:**
- 任职子表单中"所属组织""认证类型（改名为任职类型）"两个必填字段的标签在加上必填星号后不换行，两列保持对齐。
- 前端展示文案统一由"认证类型"改为"任职类型"，覆盖表单标签、必填校验提示、下拉框 placeholder、详情表格列标题。

**Non-Goals:**
- 不改字典类型 `position_type` 本身在字典管理模块中的名称/编码/种子数据（`V4__seed_dict_position_type.sql` 中的 `name` 字段维持"认证类型"不变，这是字典管理模块的数据，超出本次前端文案调整的范围）。
- 不改后端 DTO（`UserPositionRequest`/`UserPositionVO`）字段注释与校验提示文案，也不改后端字段名 `positionType`——这些是后端内部命名，与前端展示文案解耦，不在本次范围。
- 不重新设计任职子表单的整体布局或响应式断点。

## Decisions

- **文案改名范围**：只改 `UserManagementView.vue` 里面向用户展示的文本（`el-form-item` 的 `label`、`el-select` 的 `placeholder`、校验规则 `message`、详情表格的 `el-table-column label`），不动数据层字段名 `positionType` 和后端任何代码/注释/校验消息，避免影响 API 契约与既有测试。
- **label-width 修复方式**：把"所属组织""认证类型/任职类型"两个 `el-form-item` 的 `label-width` 从 `76px` 改为 `90px`，直接复用项目已验证的惯例值，不引入额外 CSS（如 `white-space: nowrap` 覆盖）。这两个字段在子表单的 2 列网格里正好是同一行（第一行），改动后该行两列宽度一致，不影响其余行（"任职地址"/"任职电话"、"显示序号"/"备注"）继续使用 `76px`，因为它们不是必填项，没有星号导致的换行问题。
  - 备选方案（未采用）：把子表单全部 6 个字段的 `label-width` 统一改成 `90px`——非必填字段本身不会换行，统一改动没有必要，且会让子表单整体更宽，挤压输入框可用宽度。
  - 备选方案（未采用）：给 `.el-form-item__label` 加 `white-space: nowrap` 强制不换行——治标不治本，字体/浏览器渲染差异下仍可能因宽度不足发生标签文字被裁切或与星号重叠，不如直接给够宽度可靠。

- **组织下拉树默认全部收起**：`el-tree-select` 内部复用 `el-tree`，`default-expand-all` 会无条件展开全部层级，节点一多下拉面板就很长，不利于定位目标组织。方案是直接移除 `default-expand-all`，且不传 `default-expanded-keys`（`el-tree`/`el-tree-select` 在两者都缺省时默认所有节点收起，只展示顶层），不需要额外的 `computed` 或响应式同步逻辑，也不需要保留/新增任何"默认展开第一层"的派生状态。用户点开下拉后先看到顶层组织列表，点击某个有子节点的组织即可展开下一层，逐层展开。
  - 备选方案（未采用，已废弃）：仅默认展开第一层级（通过 `computed` 从 `orgTree` 顶层节点 id 派生 `default-expanded-keys`）——这是上一版本的实现，但用户明确要求"全部收紧"，第一层默认展开不满足这个诉求，故改为完全不展开。
  - 备选方案（未采用）：改用 `el-tree-select` 的懒加载（`lazy` + `load`）按需向后端请求子节点——当前组织树接口是一次性返回全量数据（见 `fetchOrgTree` 注释"一次性加载，不需要防环处理"），引入懒加载需要新增后端分层查询接口，超出本次"仅调整默认展开状态"的范围。

## Risks / Trade-offs

- [风险] 文案改名遗漏某处引用（如某个校验提示或注释里的"认证类型"字样）→ 缓解：改动前已通过 `Grep` 定位全部前端 "认证类型" 出现位置（仅 `UserManagementView.vue` 内 5 处，另有 `dict.ts`/`dict` 类型文件里的 2 处仅为代码注释、非用户可见文案，本次不改）。
- [权衡] label-width 的修复是针对本项目已知的 76px→90px 惯例做的局部调整，不是通用的"必填星号防换行"组件级方案；如果后续别的表单又复现同类问题，仍需要逐处对齐 90px 惯例或另行沉淀公共样式。
- [权衡] 默认全部收起意味着即使目标组织是某个顶层节点下第一个子节点，用户也需要多点一次展开——这是"全部收紧"需求本身的取舍（避免下拉面板过长），不做特殊处理。
