## Context

组织管理页面 `.org-management` 用 CSS Grid 双栏布局（`grid-template-columns: 280px 1fr`）承载左侧组织树和右侧表格面板。右侧表格有 8 列（含 2 个 `min-width` 列 + 6 个 `width` 固定列）加一个 `fixed="right"` 的操作列，列宽之和（约 920px 固定宽度 + 260px 最小宽度 ≈ 1180px）在常见笔记本视口下会超过 `1fr` 轨道实际可分配的宽度。

## Goals / Non-Goals

**Goals:**
- 让"新增"按钮（位于右侧面板 `.org-panel__header` 里，和表格是同级但不同的元素）在任意视口宽度下始终可见，不随表格是否超宽而被挤出视口。
- 表格列本身仍然可以在需要时横向滚动查看（不强行压缩列宽导致内容截断），但滚动范围应限定在表格自身内部，不应带动整个页面/面板一起横向溢出。
- 顺带把归档后已完成的几处后端/前端维护性修复补记进本次 change 的 tasks，作为可追溯记录。

**Non-Goals:**
- 不重新设计表格列宽或响应式断点下的列显隐策略（不在本次范围）。
- 不改变本次涉及的后端修复（MapStruct 静态化、mybatis.conf 外置、`@MapperScan`）已经确定的技术方案，本次只是把它们记录进 OpenSpec。

## Decisions

- **根因**：CSS Grid 的已知陷阱——grid item 的隐式 `min-width` 默认是 `auto`，即"不小于其内容的最小内在宽度"。`.org-panel--table` 作为 `1fr` 轨道的 grid item，其内容（`el-table`，列宽之和 ≈ 1180px）撑开了这个隐式最小宽度，导致浏览器把整个面板（含面板头部的"新增"按钮）撑宽到超过视口，从而需要横向滚动整个页面/面板才能看到按钮，而不是仅仅在表格内部滚动。
- **修复方式**：在 `.org-panel` 上显式设置 `min-width: 0`，覆盖 grid item 的隐式最小宽度，让面板可以收缩到轨道分配的实际宽度；表格内容超宽时，滚动条会正确地出现在 `el-table` 自身的内部滚动容器（`.el-table__body-wrapper`，Element Plus 内置行为，无需额外样式），而面板头部（含按钮）不再随之被撑宽。
  - 备选方案（未采用）：把每列 `width` 全部改成响应式/百分比或减少列数——改动更大且会牺牲信息密度，本次问题的本质是布局约束缺失而非列设计不合理，`min-width: 0` 是最小、最直接、风险最低的修复。
  - 备选方案（未采用）：给 `.org-panel--table` 加 `overflow-x: auto` 让面板自己滚动——会把表头（"下级组织"标题 + "新增"按钮）也一起卷入横向滚动区域，问题依旧存在，不如让滚动范围精确限定在表格本身。

## Risks / Trade-offs

- [风险] `min-width: 0` 是 CSS Grid 里定位精确但容易被忽视的修复点，后续如果新增其他宽内容的 grid item 面板，若不知道这个约定，可能重犯同样的问题 → 缓解：本次在 CLAUDE.md 或组件注释里没有额外新增规则文档，因为这是通用 CSS 知识而非项目特有约定；如果后续同类问题复发，再考虑是否需要在前端约定里显式记录。
- [权衡] 表格本身在窄视口下仍然需要横向滚动才能看到全部列——这是有意保留的行为（信息密度 vs 响应式收窄的取舍不在本次范围内），本次只保证滚动被约束在表格内部、不影响按钮可达性。
