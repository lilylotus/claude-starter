## Context

`tab_org` 目前只有 `V1__init_tab_org.sql` 一个迁移版本，且真实本地库已经跑过这个版本（`flyway_schema_history` 里记了 v1）。新增字段需要一个新的迁移版本，不能修改 V1（Flyway 迁移脚本一旦应用就不可回改，改了会导致校验和不匹配报错）。

列表页当前 8 个数据列 + 操作列的宽度总和（约 1180px）经常超出面板可用宽度，这也是上一个 change（`fix-org-management-followups`）里修复"横向溢出挡住新增按钮"问题的直接背景；这次去掉 4 个审计字段列，从根源上进一步减少列表的宽度压力（虽然那次的 CSS 修复已经让这种溢出被约束在表格内部、不再影响按钮可达性，但列表本身依然会更清爽）。

## Goals / Non-Goals

**Goals:**
- 列表页只保留浏览时高频需要的列：组织名称、编码、状态、显示序号。
- 新增只读的"组织详情"弹窗，展示全部字段（含备注、审计字段），复用已有的 `GET /api/orgs/{id}` 接口，不新增后端接口。
- `remark` 作为可选自由文本字段，创建/编辑时可填可不填。

**Non-Goals:**
- 不改变现有的 `GET /api/orgs/children` 返回结构（后端 `OrgVO` 本来就包含全部字段，只是前端列表不再渲染其中几列）——不是 breaking change，不需要新增字段过滤参数。
- 不给 `remark` 加长度校验之外的其他业务规则（如敏感词过滤），保持最小实现。

## Decisions

- **迁移脚本版本**：新建 `V2__add_org_remark.sql`，`ALTER TABLE tab_org ADD COLUMN remark VARCHAR(255) NULL COMMENT '备注' AFTER show_order;`——放在 `show_order`之后、`ext1` 之前，语义上更贴近"业务字段"而不是"预留扩展字段"。不复用/修改 V1。
- **详情弹窗数据来源**：复用现有 `orgApi.getOrgById(id)`（已经是 `OrgManagementView.vue` 编辑弹窗在用的同一个接口），不新增后端接口，也不新增前端 API 封装函数。详情弹窗和编辑弹窗是两个独立的 `el-dialog`（详情只读展示，编辑仍是表单），共享同一次 `getOrgById` 调用模式但状态各自独立，避免耦合两个弹窗的开关逻辑。
- **详情入口位置**：操作列新增"详情"链接按钮，放在"编辑"之前（浏览优先于编辑的操作顺序），复用现有 link-button 视觉风格。
- **表单新增备注输入框**：用 `el-input type="textarea"` （2-3 行），不设置 `required` 校验规则（可选字段）。
- **审计字段列移除后的宽度重新分配**：不显式改动剩余列的 `width`/`min-width`（保持既有像素值），操作列因新增一个"详情"按钮而略微加宽（`200px` → `240px`）以容纳四个 link-button。不做进一步的响应式断点设计（超出本次范围）。

## Risks / Trade-offs

- [风险] `remark` 未做长度上限校验（前端表单侧），如果用户输入超过数据库 `VARCHAR(255)` 限制会导致后端保存失败并抛出数据库层错误，而不是友好的表单校验提示 → 缓解：这是已知的最小实现取舍，如果后续出现真实问题，再补充前端 `maxlength` + 校验规则；数据库层面 `VARCHAR(255)` 本身有兜底。
- [权衡] 详情弹窗和编辑弹窗都各自独立调用 `getOrgById`，选中同一行连续打开"详情"再"编辑"会产生两次网络请求——可接受，数据量小、非高频操作，不引入额外缓存复杂度。
