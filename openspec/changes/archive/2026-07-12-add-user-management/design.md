## Context

组织管理（`org-management`）确立了基础设施惯例（`cn.nihility.rbac` 包结构、`common` 统一响应、Flyway + `tab_` 前缀、`status` 身兼启停用与逻辑删除语义）；字典管理（`add-dict-management`，需先于本 change 完成）提供了"认证类型"（`position_type`：主职/兼职/挂职）的字典数据来源。用户管理是身份体系中第三个模块，需要同时挂靠组织（任职关系）和字典（认证类型），是第一个"聚合两个既有模块数据"的业务模块。

用户已明确两点产品决策：（1）一个用户可以同时挂载到多个组织，即任职关系是 1:N；（2）认证类型来自通用字典模块，而非后端写死枚举。

## Goals / Non-Goals

**Goals:**
- 用户主数据的增删改查、启停用、按姓名/手机号/身份证号模糊搜索的分页查询。
- 用户可关联 0 到多条任职记录，每条记录独立维护组织、认证类型、任职地址/电话等信息，且各自保留独立的创建/更新审计信息。
- 前端提供列表 + 表单（内嵌任职子表单）的管理界面。

**Non-Goals:**
- 不做用户与角色的关联（那是后续独立 change 的范围）。
- 不做登录账号/密码相关能力（当前登录仍是 `src/api/auth.ts` 里的本地模拟实现，与本模块的"用户主数据"是两个不同的概念，暂不打通）。
- 不给任职记录单独暴露 CRUD 接口（不做成前端可以脱离用户表单单独管理任职记录的界面）。
- 不做身份证号的国家标准校验码校验（只做基础格式校验），不做手机号运营商归属地校验。

## Decisions

- **任职记录随用户创建/更新接口整体提交，按 `id` 做增量 diff，而非独立的子资源 CRUD 接口**：任职记录数量少（通常个位数）、且总是伴随用户表单一起编辑，独立暴露 `POST/PUT/DELETE /api/users/{id}/positions/{positionId}` 会让前端需要多次请求编排创建时序（先建用户拿到 id，再逐条建任职），增加不必要的交互复杂度。选择"整体提交 + 服务端 diff"：请求体 `positions` 数组中，携带 `id` 的项按该 id 更新（若不属于当前用户则拒绝，保留其原始 `createBy`/`createTime`，刷新 `updateBy`/`updateTime`）；不携带 `id` 的项作为新记录插入（全新审计字段）；用户当前已有但本次请求 `positions` 数组中未出现的记录，物理删除。这样前端表单可以用一个"添加/编辑/删除任职行"的本地子表单状态，点一次保存整体提交。
  - 代价：如果两个浏览器标签同时编辑同一个用户的任职记录，后保存的一方会整体覆盖先保存的一方未感知到的变更（没有做逐行乐观锁）。当前判断用户管理场景下并发编辑同一用户的概率低，不引入版本号字段；如果后续出现并发覆盖问题，可以给 `tab_user_position` 加 `version` 字段做乐观锁。
  - 实现细节：`UserServiceImpl.syncPositions()` 落地了上述 diff 逻辑——先按 `userId` 查出既有任职记录列表建立 `id -> entity` 映射，校验请求中携带的 `id` 是否都属于当前用户（否则整体拒绝），再逐条按"有无 `id`"分流为更新/插入，最后对既有记录里未出现在本次请求 `keptIds` 集合中的 id 做批量物理删除。批量删除使用 MyBatis-Plus 3.5.16 提供的 `BaseMapper#deleteByIds`（而非已废弃的 `deleteBatchIds`）。
- **详情查询与分页列表查询对任职记录的回填策略不同**：`getById()` 会额外查询任职记录并通过一次 `orgId IN (...)` 批量查询回填每条任职记录的 `orgName`，避免逐条查询组织表造成 N+1；而分页列表 `getPage()` 返回的 `UserVO` 不包含任职记录（也就不需要回填 `orgName`），因为列表场景下一页多条用户记录会成倍放大任职记录的查询与组织名回填开销，而列表页本身不需要展示任职明细，用户点开详情/编辑弹窗时才按需查询。
- **任职记录物理删除，不做逻辑删除**：任职记录是纯粹依附于用户的明细行，没有独立的"停用"业务含义（启停用只在用户主体维度存在），被移除的任职记录不需要保留痕迹供恢复，因此直接物理删除，不像 `tab_org`/`tab_user` 那样用 `status = -1000` 表达逻辑删除。
- **删除（逻辑删除）用户不级联处理其任职记录**：`DELETE /api/users/{id}` 只把 `tab_user.status` 置为 `-1000`，不物理删除或修改其名下的 `tab_user_position` 行。因为一旦父用户被逻辑删除，`GET /api/users/{id}`、列表查询都已经不会再返回该用户，任职记录成为不可达的孤儿数据，等同于被删除的效果，没有必要额外遍历删除子表，减少一次写操作；如果后续需要彻底清理，可以在物理清库层面处理。
- **认证类型以字典项编码（`code`，如 `primary`）存储在 `tab_user_position.position_type` 字段，而非外键关联 `tab_dict_item.id`**：与字典模块 `design.md` 中"业务模块按字典类型编码消费"的约定一致——业务代码只应该硬编码稳定的语义标识（字典类型编码 `position_type` + 字典项编码 `primary`/`part_time`/`temporary`），不应该依赖字典表内部自增 id。后端不对 `position_type` 的取值做运行时校验（不反查字典表确认该编码当前仍启用），由前端下拉框（数据源为字典模块的只读查询接口）保证只能选到当前启用的合法值，这是开发期约定而非运行时强校验，与字典模块设计文档中记录的同一权衡保持一致。
- **`org_id` 为任职记录必填字段，不允许"任职但不挂靠任何组织"**：需求原文"支持选择是否挂载到某个组织下面"，在 1:N 模型下语义变为"是否存在任职记录"——用户可以没有任何任职记录（对应"不挂载"），但只要存在一条任职记录，它就必须归属某个具体组织，不存在"任职记录的组织为空"的中间状态，语义更清晰，也避免前端组织选择器需要处理"未选择"和"选择顶级"两种空值语义的歧义（`org-management` 里"顶级组织"用 `parentId = 0` 表达，是真实语义，不能被复用为"无组织"）。
- **用户编号（`code`）与身份证号（`idCard`）在未删除用户范围内唯一，手机号不做唯一性约束**：编号类似工号，身份证号是自然人的唯一标识，两者重复大概率是录入错误或重复建档，值得在创建/更新时校验拦截；手机号在现实中可能存在家庭共用、员工更换等情况，且需求未明确要求唯一，因此不加唯一性约束，仅做基础格式校验。
- **性别用整型常量 `UserGender`（`0` 未知/`1` 男/`2` 女），不复用字典模块**：性别取值极其稳定、几乎不会变化，且是通用语言学概念而非本系统的业务配置项，延续 `OrgStatus` 的做法用后端常量类表达，不值得为它去掉字典模块的复用收益（字典模块的核心价值是给运营可配置的业务枚举，性别不是"运营可能会新增选项"的那类数据）。
- **列表查询的模糊搜索用三个独立可选参数 `name`/`mobile`/`idCard`，组合时为 AND 关系**：对应前端三个独立搜索框的直觉用法（分别填写、同时填写多个时进一步收窄结果），比"单个关键字模糊匹配任意字段"更符合"手机号、身份证号、姓名模糊搜索"这句需求里三个字段并列、各自对应输入框的表述。

## Risks / Trade-offs

- **[风险] 任职记录整体提交覆盖式更新，无并发控制** → 见上文"任职记录随用户创建/更新接口整体提交"决策项，多人同时编辑同一用户的任职记录时后提交者会覆盖先提交者未感知的变更。缓解：当前业务场景判断并发编辑概率低，不引入乐观锁；后续如有需要可加 `version` 字段。
- **[风险] `position_type` 不做运行时校验** → 如果绕过前端直接调用接口，可以传入任意字符串作为认证类型编码，不会被拒绝，只是前端渲染时找不到对应标签会显示原始编码。缓解：这是与字典模块一致的既定权衡（业务模块不反查字典表做强校验），如果后续需要更强的数据完整性保证，可以在 service 层加一次只读查询校验，但会引入用户模块对字典模块的运行时依赖（当前只有编译期/文档约定层面的依赖）。
- **[权衡] 删除用户不级联清理任职记录** → 长期会在 `tab_user_position` 表里积累指向已删除用户的孤儿行，增加表体积但不影响查询正确性（父用户不可达，行为等同于删除）。接受这个权衡，避免删除接口引入额外的子表写操作。
