## MODIFIED Requirements

### Requirement: 用户详情查询
系统 SHALL 提供按 id 查询用户详情的接口，返回结果包含用户主数据全部字段、其名下全部未被逻辑删除的任职记录（含各自的组织名称、认证类型编码、任职地址、任职电话、显示序号、备注、状态及各自独立的创建人/创建时间/更新人/更新时间），以及用户自身的创建人/创建时间/更新人/更新时间。已被逻辑删除（`status = -1000`）的任职记录 SHALL 不出现在返回的任职记录列表中。

#### Scenario: 查询存在的用户
- **WHEN** 客户端调用 `GET /api/users/{id}` 且该用户存在且未被删除
- **THEN** 系统返回该用户完整信息及其未被逻辑删除的任职记录列表（按 `showOrder` 降序、相同时按 `id` 升序排列）

#### Scenario: 查询不存在的用户
- **WHEN** 客户端调用 `GET /api/users/{id}` 且该 id 不存在或已被逻辑删除
- **THEN** 系统返回业务错误（非零 `code`），不返回 HTTP 500

#### Scenario: 用户名下没有任职记录
- **WHEN** 客户端调用 `GET /api/users/{id}` 且该用户当前没有任何未被逻辑删除的任职记录
- **THEN** 系统返回该用户信息，任职记录列表为空数组

#### Scenario: 已被逻辑删除的任职记录不出现在详情中
- **WHEN** 该用户名下某条任职记录的 `status` 为 `-1000`（已通过任职管理页面逻辑删除）
- **THEN** 该条任职记录不出现在 `GET /api/users/{id}` 返回的任职记录列表中

### Requirement: 用户任职记录的整体更新
系统 SHALL 在更新用户接口的请求体中接受完整的任职记录列表（`positions`），并按以下规则同步，同步的基准范围为该用户当前未被逻辑删除（`status != -1000`）的任职记录：请求项携带 `id` 且该 `id` 属于当前用户未被逻辑删除的既有任职记录时，更新该记录字段（不修改其 `status`），保留其原始创建人/创建时间，刷新更新人/更新时间；请求项未携带 `id` 时，作为新任职记录插入，`status` 显式置为 `2000`（启用）；当前用户未被逻辑删除的既有任职记录中，凡其 `id` 未出现在本次请求 `positions` 列表中的，系统 SHALL 物理删除。已被逻辑删除的任职记录不参与本次 diff（既不会被当作"需要保留"的既有记录，也不会因未出现在请求列表中而重新触发删除动作之外的副作用）。

#### Scenario: 保留既有任职记录的创建审计信息
- **WHEN** 客户端调用 `PUT /api/users/{id}`，`positions` 中某一项携带了该用户既有任职记录的 `id` 并修改了其 `positionAddress`
- **THEN** 系统更新该记录的 `positionAddress`，`createBy`/`createTime` 保持不变，`updateBy`/`updateTime` 刷新为本次操作，`status` 不受影响

#### Scenario: 新增任职记录默认启用
- **WHEN** 客户端调用 `PUT /api/users/{id}`，`positions` 中包含一项未携带 `id` 的新记录
- **THEN** 系统为该用户新增一条任职记录，`status` 为 `2000`（启用），拥有全新的创建人/创建时间

#### Scenario: 移除任职记录
- **WHEN** 客户端调用 `PUT /api/users/{id}`，`positions` 列表中不再包含该用户某条既有任职记录的 `id`
- **THEN** 系统物理删除该条任职记录

#### Scenario: 请求携带不属于当前用户的任职记录 id 时拒绝
- **WHEN** 客户端调用 `PUT /api/users/{id}`，`positions` 中某一项携带的 `id` 属于另一个用户的任职记录
- **THEN** 系统拒绝该次更新，返回业务错误（非零 `code`）

#### Scenario: 清空全部任职记录
- **WHEN** 客户端调用 `PUT /api/users/{id}`，携带空数组 `positions: []`，且该用户此前存在未被逻辑删除的任职记录
- **THEN** 系统删除该用户此前全部未被逻辑删除的任职记录

#### Scenario: 已被任职管理逻辑删除的记录不参与 diff 也不会被重新携带
- **WHEN** 该用户名下存在一条 `status = -1000` 的任职记录（此前已通过任职管理页面删除），客户端调用 `PUT /api/users/{id}` 且 `positions` 中不包含该记录的 `id`
- **THEN** 系统不会因为该记录"未出现在请求列表"而对已删除状态产生额外影响，该记录依旧不出现在后续查询结果中
