## Context

组织管理模块（`add-org-management`）已经确立了项目的基础设施：包名 `cn.nihility.rbac`、统一响应 `common` 包、Flyway 迁移 + `tab_` 前缀约定、`status`（`2000`/`3000`/`-1000`）身兼启停用与逻辑删除语义的惯例。字典管理是第二个业务模块，延续这套约定；它本身不挂靠组织，是一个独立的、扁平两层结构（字典类型 → 字典项）。

即将到来的用户管理模块需要"认证类型：主职/兼职/挂职"这个枚举，用户明确要求不写死为后端常量，而是先建一个通用字典管理模块，本 change 就是这个前置模块。

## Goals / Non-Goals

**Goals:**
- 提供字典类型、字典项两级数据的完整增删改查、启停用能力。
- 提供一个轻量只读接口，让任意业务模块按字典类型编码取启用状态的字典项列表，不需要感知分页/权限。
- 预置用户管理模块要用到的 `position_type`（主职/兼职/挂职）字典数据，避免下一个 change 还要补种子数据。
- 前端提供类型 + 项的主从管理界面，视觉上延续项目"链式连接"语言（圆点+虚线）。

**Non-Goals:**
- 不做字典的多语言/国际化。
- 不做字典项的树形/多级嵌套（字典项只有一层，不像组织支持无限级 `parentId`）。
- 不引入前端全局的"字典自动加载并缓存到 Pinia store 供所有页面使用"的框架性能力——用户管理模块直接调用字典模块暴露的只读查询接口即可，如果未来出现更多消费方导致重复请求成为问题，再抽象成公共 composable。
- 不做字典类型/字典项的操作审计日志（复用现有 `create_by`/`update_by`/`create_time`/`update_time` 字段即可，不接入独立的审计系统）。

## Decisions

- **两张表：`tab_dict_type` + `tab_dict_item`，而非单表自关联（像 `tab_org` 用 `parent_id` 表达层级）**：字典只有"类型 → 项"两层固定层级，不需要无限递归，用两张职责清晰的表比单表自关联更直观，查询也更简单（不需要过滤"根节点"）。
- **字典项通过 `dict_type_id`（外键关联 `tab_dict_type.id`）而非 `dict_type_code` 关联**：与 `tab_org` 用 `parent_id` 关联 id 一致的惯例；但对外的只读查询接口以 `dict_type_code`（如 `position_type`）作为入参，因为业务代码里字典类型编码是稳定的语义标识，而 id 是数据库内部细节，不应该被业务模块硬编码依赖。
- **状态语义复用 `2000`/`3000`/`-1000`**：与 `OrgStatus` 保持一致，新增 `DictStatus` 常量类而不是复用 `OrgStatus`（不同模块的常量类保持独立，避免耦合，即便值相同）。
- **字典项编码唯一性范围：同一 `dict_type_id` 下未删除字典项**：不同字典类型下可以出现相同编码（如两个字典类型都用 `1`/`2`/`3` 做编码），唯一性校验按 `(dict_type_id, code, status != DELETED)` 判断，与组织模块编码全局唯一的范围不同，因为字典项的编码含义依赖其所属类型。
- **字典类型编码全局唯一（未删除范围内）**：字典类型编码（如 `position_type`）是跨模块的语义标识符，必须全局唯一，唯一性校验按 `(code, status != DELETED)`。
- **只读查询接口 `GET /api/dicts/items?typeCode={code}` 返回精简 VO（`code`/`label`/`showOrder`），不复用管理列表的分页 VO**：消费方（下拉框）只关心"启用状态、按显示序号排序"的键值对列表，不需要 id、审计字段等管理视图才用得到的信息；接口内部按 `status = ENABLED` 过滤，`typeCode` 对应的字典类型本身若被禁用/删除，则返回空列表而非报错（避免因为字典类型被误停用导致业务表单直接报错崩溃，静默降级为下拉框无选项）。
- **前端左侧字典类型用普通分页列表而非树**：字典类型之间没有层级关系，用 `el-table` 列表 + 分页即可，比照组织管理树形选择器的复杂度不需要在这里重现；右侧字典项表格的主从联动方式（选中左侧一行 → 右侧展示其字典项分页列表）与组织管理"选中树节点 → 展示直属子组织"的交互保持一致，保留用户已经熟悉的操作模式。
- **种子数据通过 Flyway 迁移 SQL 而非应用启动时的 `CommandLineRunner` 写入**：`position_type` 字典类型及其三个字典项是本 change 承诺交付给下一个 change 的前置数据，写成迁移脚本里的 `INSERT`，保证任何环境执行迁移后数据必然存在，不依赖应用代码里容易被后续重构遗漏的初始化逻辑。实现上拆成两个迁移脚本：`V3__init_tab_dict.sql` 建表，`V4__seed_dict_position_type.sql` 插种子数据；字典项的 `INSERT` 不硬编码 `dict_type_id`（迁移执行时自增 id 具体是多少无法预知），而是用 `INSERT INTO tab_dict_item (...) SELECT id, ... FROM tab_dict_type WHERE code = 'position_type'` 依据字典类型编码反查其自增 id，保证外键关联在任何环境下都正确，不依赖"这是本库第一条记录所以 id 必然是 1"这类脆弱假设。

## Risks / Trade-offs

- **[风险] 只读查询接口对被禁用字典类型静默返回空列表** → 如果运营误停用了一个正在被业务表单使用的字典类型，前端下拉框会静默变空而不是报错提示，可能不易被发现。缓解：这是刻意的降级策略（保证业务表单不因字典配置问题而整体报错），后续如果需要更强的可观测性，可以在字典管理列表页对"仍被引用中的字典类型"做标记提醒，不在本 change 范围内。
- **[风险] 字典项编码唯一性按字典类型分别校验** → 如果后续有人在只读查询接口的调用方误传了错误的 `typeCode`，会拿到另一个字典类型下恰好同编码的项，语义错误但不会报错。缓解：`typeCode` 由调用方硬编码在业务代码里（如用户管理模块写死 `position_type`），属于开发期约定，不做运行时校验；这与组织模块编码全局唯一因而不存在此问题的情况不同，属于两个模块结构差异带来的固有权衡。
- **[权衡] 种子数据写在迁移脚本里** → 如果后续需要修改种子数据的初始文案（如把"挂职"改成别的说法），只能通过新的迁移脚本 `UPDATE`，不能直接改历史迁移文件（Flyway 已应用的迁移不可变）。这是 Flyway 的标准约束，接受这个权衡以换取环境间数据一致性的保证。
