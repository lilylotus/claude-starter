## Context

两个独立缺陷，已各自修复并通过 `npm run build` 验证，本文档做追溯性记录。

- Element Plus `el-table-column` 的列宽规则：只设置 `width` 的列是固定宽度；只设置 `min-width`（不设
  `width`）的列会参与"剩余可用宽度"的分配（弹性列）。`OperationLogManagementView.vue` 原来的写法是
  固定宽度与 `min-width` 混用且分配不均——只有"操作模块"（`min-width=110`）与"被操作对象"
  （`min-width=140`）两列是弹性列，其余是固定宽度；当表格容器较宽时，剩余空间几乎全部被这两个
  弹性列瓜分，导致它们被拉伸到远超内容实际需要的宽度，视觉上表现为"这一列和相邻列之间空出一大截"。
  排查过程中一度把全部列都改成固定 `width`，则反过来出现列宽总和小于容器宽度、表格右侧留白、
  看起来"只占界面一半"的问题。
- `frontend/src/api/request.ts` 的响应拦截器里，`body.code === 401` 分支在满足
  `isRefreshValid` 时会 `await triggerRefresh()` 后 `return request(originalConfig)` 重试原始
  请求；这个重试调用会重新进入同一个响应拦截器，如果重试后的响应仍然是 `401`，原代码没有任何
  区分"这是第一次 401 还是重试后又 401"的手段，会被当成全新的一次过期处理，再次刷新、再次重试，
  无限递归。`login-log-management` 页面只是第一个复现场景，缺陷本身属于 `password-login-auth`
  能力的横切逻辑，与具体页面无关。

## Goals / Non-Goals

**Goals:**
- 把"操作日志列表列宽自适应、不出现异常间距/整体宽度不足"的行为固化为可测试的 spec 要求。
- 把"静默刷新最多重试一次"固化为 `password-login-auth` 能力的 spec 要求，防止未来类似的 401
  处理逻辑改动重新引入无限递归。

**Non-Goals:**
- 不重新设计操作日志页面的整体布局/新增筛选能力。
- 不改动 access-key/refresh-key 的签发、有效期、Redis 存储等后端会话机制。

## Decisions

### 1. 列宽分配：多个可伸缩列共享剩余空间，而不是单一弹性列独占
把"操作模块""资源类型""被操作对象""操作人"四列统一使用 `min-width`（而不是只让其中一两列
弹性），配合 `show-overflow-tooltip` 防止超长内容换行；"操作时间""操作类型""操作发起 IP""操作"
四列内容长度确定或有上限，继续使用固定 `width`。多个弹性列会按各自 `min-width` 的比例分摊剩余
空间，单个列不会被过度拉伸，代价是每个弹性列都可能比其内容实际需要的宽度略宽，但分散在四列上
比集中在一两列上视觉观感更均匀，同时保证表格能撑满可用展示区域。

**备选方案**：给表格一个显式的最大宽度并居中，超出部分留白。未采用，因为这仍然会在宽屏上出现
"表格没有撑满可用区域"的观感问题，且不是用户反馈想要的效果（用户明确要求撑满宽度）。

### 2. 静默刷新重试上限：同一原始请求最多重试一次
在 `originalConfig` 对象上打一个 `_retriedAfterRefresh` 标记（该对象在重试时是同一个引用，
标记能跨递归调用持续存在）；进入 401 分支时先检查该标记，已标记过的请求不再触发刷新，直接跳转
登录页。选择"每个原始请求最多重试一次"而不是"限制总刷新次数"或"加一个全局冷却时间"，是因为
这个粒度最贴合问题本质——单次 access-key 刷新要么解决问题（重试成功），要么说明问题不是简单的
access-key 过期（此时应该让用户重新登录，而不是猜测再刷新一次是否会有不同结果）。

**备选方案**：给 `triggerRefresh()` 增加一个全局的"最近刷新时间"节流窗口。未采用，因为节流窗口
的时长选取比较随意，且无法精确对应到"这一个原始请求已经重试过一次"这个更明确的语义，还可能
误伤短时间内多个不同请求各自合理的首次 401 刷新需求。

## Risks / Trade-offs

- [弹性列分摊空间后，具体每列的最终宽度不再是设计时精确指定的像素值，不同分辨率下略有差异] →
  可接受：目标本来就是"自适应可用宽度"，不是像素级还原设计稿。
- [静默刷新限制为一次重试后，如果未来出现"access-key 确实需要刷新两次才能生效"的合理场景（目前
  没有这种场景），会被误判为登录失效] → 可接受：当前后端签发/校验 access-key 是同步生效的，不存在
  这种场景；如果未来引入类似场景，应该在后端解决"刷新后立即生效"的一致性问题，而不是在前端用
  更多次重试掩盖。

## Migration Plan

纯前端代码调整，无数据迁移，无需特殊部署步骤；已随日常前端构建发布。
