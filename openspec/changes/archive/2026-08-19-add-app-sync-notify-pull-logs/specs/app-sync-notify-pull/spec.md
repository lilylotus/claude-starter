## ADDED Requirements

### Requirement: 通知日志记录与查询
系统 SHALL 在每次向应用发起通知请求（无论成功或失败）后，把本次通知的数据类型、被变更
对象 id、实际使用的回调地址（发起请求前读取的地址快照，不是查询时的当前配置值）连同已有
的状态、HTTP 状态码、错误摘要一并落库。系统 SHALL 提供管理端查询接口，按应用 id 分页
查询该应用的通知日志，支持按时间范围过滤、按通知状态（成功/失败）过滤；不传过滤条件时
返回该应用全部通知日志，按时间倒序排列。日志写入失败 SHALL NOT 影响本次通知请求本身的
发起与结果判定。

#### Scenario: 通知记录携带数据类型、bizId 与回调地址快照
- **WHEN** 系统向某应用发起一次组织新增变更的通知请求
- **THEN** 落库的通知日志记录数据类型为"组织"、`bizId` 为该组织 id、`notify_url` 为
  本次请求实际使用的回调地址

#### Scenario: 按时间范围查询通知日志
- **WHEN** 管理员查询某应用的通知日志，传入一段时间范围
- **THEN** 系统只返回该时间范围内产生的通知日志，按时间倒序分页返回

#### Scenario: 按状态过滤通知日志
- **WHEN** 管理员查询某应用的通知日志，传入状态过滤为"失败"
- **THEN** 系统只返回该应用状态为失败的通知日志

#### Scenario: 日志写入失败不影响通知主流程
- **WHEN** 系统发起一次通知请求且回调成功，但落库通知日志时发生异常
- **THEN** 本次通知请求仍视为已正常完成，不因日志写入失败而报错或重试通知

### Requirement: 拉取日志记录与查询
系统 SHALL 在每次外部应用调用拉取接口（按数据类型与 id 拉取、按序列号批量拉取）后，
记录归属应用、拉取方式、请求的数据类型（按序列号拉取未指定数据类型时为空）、请求参数
摘要、本次返回的记录条数与请求时间。系统 SHALL 提供管理端查询接口，按应用 id 分页
查询该应用的拉取日志，支持按时间范围过滤；不传过滤条件时返回该应用全部拉取日志，按
时间倒序排列。日志写入失败 SHALL NOT 影响本次拉取请求的响应结果。

#### Scenario: 按 id 拉取产生一条拉取日志
- **WHEN** 某应用调用按数据类型与 id 拉取接口，请求了 3 个 bizId，最终返回 2 条记录
- **THEN** 系统落库一条拉取日志，拉取方式为"按 id"，返回记录条数为 2

#### Scenario: 按序列号拉取产生一条拉取日志
- **WHEN** 某应用调用按序列号批量拉取接口，未传数据类型过滤
- **THEN** 系统落库一条拉取日志，拉取方式为"按序列号"，数据类型为空

#### Scenario: 按时间范围查询拉取日志
- **WHEN** 管理员查询某应用的拉取日志，传入一段时间范围
- **THEN** 系统只返回该时间范围内产生的拉取日志，按时间倒序分页返回

#### Scenario: 日志写入失败不影响拉取主流程
- **WHEN** 某应用发起一次拉取请求且正常返回结果，但落库拉取日志时发生异常
- **THEN** 本次拉取请求仍正常返回结果给调用方，不因日志写入失败而报错
